# 8. A guarded client is the only way live tests write or delete dashboards

Date: 2026-11-05
Status: Accepted

<!-- This ADR is committed to the repository. Write it for an outside reader: no plan row, risk, exit or external-decision IDs, no internal tickets or links. Scenario labels S1, S2 are fine. -->

## Context

### Problem

Banana's live tests (the smoke test and the acceptance run in the test plan) need to save, load and delete dashboards on a Fusion instance that other people also use. That instance is shared. The owner of the instance allows the tests to create objects whose names start with `banana-it`, and to delete only Banana dashboard blobs that the same test run created, under an id of the form `banana-it-<run>-<n>`. Nothing else may be changed or deleted.

Banana's own code makes that rule hard to keep, because the dashboard id is the dashboard title, and the code that saves, loads and deletes handles the id inconsistently.

- A dashboard saved under an existing title silently overwrites the stored dashboard. The blob store does not refuse a second PUT to an existing id.
- Save encodes the id; load and delete do not. A title containing `?` or `#` therefore saves under the full title but is loaded and deleted under a shorter one, so a delete can remove a different dashboard from the one the user chose.
- The list screen drops the first character of any id that contains `/`, so a click on Delete for such a row sends a delete for a different id.
- When Fusion answers a save or a delete with an error, the HTTP wrapper turns the failure into a resolved promise, and the screens then report success. A failed delete looks like a deleted dashboard.
- In Solr mode, which a settings checkbox can switch on while the page is running, the same Delete button sends an XML delete-by-query to the Solr update path.
- Panels that use stream expressions put dashboard fields into an `expr` parameter without escaping, and the browser sends it with a GET. The Fusion route `/api/solr/<collection>/stream` accepts it.
- The save-to-gist button posts the whole dashboard to a public host.
- A dashboard's extra-parameters field and each panel's custom query string are appended raw to every query. A parameter such as `shards`, `qt` or `collection` changes where Solr sends the request or which handler runs it, so a query that looks like a read can become a request to another address.
- The Fusion admin UI, which the login page redirects to, posts client telemetry to `/api/ui-logs` on every page.

A test that drives Banana's UI through this code can therefore delete or overwrite something nobody created, and report success. The tests must exercise Banana's own delete path (otherwise the delete is not tested), so the guard has to sit in front of the browser as well as in front of any Node code.

A `path:line` here without an alias cites Banana at the time of writing; several of those files have changed since, so find the code by the name given. This record is the design for that guard and was accepted before it was built; its implementation, its tests and the results of the first runs are described under the verification plan. Playwright facts below come from the typings of version 1.65.0 and are vendor documentation, not the runtime's source; the implementation pins exactly that version (D9) and re-runs the local-browser tests on any change of it. The guard is test tooling under `test/live/`; it changes nothing that ships in `dist/`.

The base commit of this work is 06df7741fd61670a9ba36242ba3da5f759a121d4, but the client will be written against the integration head, which includes the fixes re-applied from the 1.6.27 to 1.6.30 releases and the Fusion defaults. ## Options considered

1. **Rely on convention: tell test authors to use only plain titles and to clean up after themselves.** Rejected because one typo, one odd title or one failed delete that the UI reports as success damages a system other people use, and a convention is not checked by anything.
2. **Guard only the Node code, and test Banana's delete by calling the client.** Rejected because the delete that must be exercised is the browser's own unencoded DELETE. A Node-only guard would leave the interesting path unguarded or untested.
3. **Restrict the test user on the server, with a role that can touch only Banana blobs.** Rejected for now: it needs a security configuration change that the owner has not allowed beyond one test user and role, and it is unverified that a role can be limited to blob ids of a given form. It remains a possible later addition; the guard does not depend on it.
4. **Filter in the test proxy (nginx) instead of in the test browser.** Rejected as the primary guard because which ids are allowed is state held by the test process (the ids this run created, and the 404 check before the first PUT). A proxy cannot know that. Static refusals in the proxy may be added later as a second layer.
5. **Use a stub instead of the shared instance.** Rejected: the point of the live run is evidence of what Fusion does with Banana's real requests. A stub proves the stub.
6. **Allow deletes by prefix (`banana-it-`) or by listing the blobs that match.** Rejected: a prefix also matches other runs, other tools and the suffix case `x-banana-it-r-1` if the pattern is not anchored, and a listing-based delete deletes whatever the listing returns.
7. **Keep the list of created ids in memory only.** Rejected: a crash would leave no record of what exists on the shared instance.
8. **Make the first PUT conditional so that Fusion refuses an overwrite.** Not available: it was not shown that the blob store honours a conditional header, and an unproven server feature cannot be the guard. The 404 check before the first PUT is the substitute, and its remaining race is a stated residual.

9. **Allow every same-origin GET.** Rejected: the shared instance forwards a GET to arbitrary Solr handlers under `/api/solr/<collection>/`, so a GET can execute a stream expression or reach an administrative handler. A read is only known to be a read on a route that was observed to be one.
10. **Continue every allowed request unchanged and rely on the route seeing the redirect.** Rejected: Playwright calls the route only for the first URL of a redirect, and a 307 or 308 makes the browser repeat the method and body at an address nobody checked.
11. **Refuse any registry directory that lies inside a git work tree.** Rejected: the maintainer's own checkout keeps its local scratch area, ignored by version control, inside the work tree, and the pre-merge run happens there. The requirement that matters is that the files can never be committed, which `git check-ignore` tests directly.

12. **Keep a deny-list of known-dangerous select parameters.** Rejected: it has to know every name that can redirect or reroute a request, and a list of `qt`, `shards.qt`, `expr`, `stmt` and `stream.*` still misses `shards`, which sends the request to an address the parameter names. No Solr source is pinned, so the list cannot be checked for completeness. An allowlist of the names Banana sends needs no such knowledge.
13. **Make the `playwright` fixture throw.** Rejected: the runner's built-in auto fixtures take `playwright` in every test and read members of it (`playwright/lib/index.js` lines 77-79, 163-164, 196-210, 352-365, 649-650 and 693-694), so every test would fail at setup. The override is a wrapper of the real module that throws only from the calls that obtain an unguarded browser or request client.

## Decision

The guard has one rule table and two enforcement points: a Node client for direct writes, and a rule set installed on every browser context for writes that Banana makes itself. Both read the same table. Everything below fails closed: a request the table does not name is refused.

Names of files are indicative; the interfaces and rules are the decision. The module lives in `test/live/fusion-client/`, and its unit tests live in `test/node/` so the existing `npm run test:node` runs them with Node's built-in runner and no Fusion.

**D1. Run identity and ids.**
- Each process that can write (the test coordinator and each Playwright worker) creates its own random identity at start: 12 lowercase hexadecimal characters from `crypto.randomBytes`. It is independent of the run's other processes and is not derived from a clock, a counter or another identity.
- Every id the process allocates is `banana-it-<identity>-<n>` with `n` counting up from 1 in that process, never reused. The module accepts ids only if they match `^banana-it-[0-9a-f]{12}-[1-9][0-9]{0,5}$` (anchored; so `x-banana-it-r-1`, a trailing newline or a trailing `?x` do not match).
- A test never builds a title by hand. It asks the module for the next id and uses it as the dashboard title (the title is the id, `src/app/services/dashboard.js:386`). That is the only way an id comes into being.
- "Owned" means: allocated by this process. Another process's id, even one that matches the pattern, is not owned.

**D2. On-disk registry, written before the write.**
- The directory comes from an environment variable (indicative name `BANANA_LIVE_REGISTRY_DIR`). It must be absolute and must already exist; the module never creates parent directories. After resolving symbolic links it must satisfy one of two tests, and the module refuses to start otherwise:
  - it is outside every git work tree (`git rev-parse --is-inside-work-tree` run in it does not print `true`); or
  - it is inside a work tree, but untracked and ignored: `git check-ignore -q` succeeds for a file path inside it, and `git ls-files` lists nothing under it.
  The point of both tests is that a registry file can never be committed. The documented default is a subdirectory of the maintainer's local scratch directory, a gitignored local directory that the checkout already excludes from version control. The module does not need to know where that is, because `git check-ignore` is the test; a fresh clone that has no such exclusion must point the variable outside the work tree or add an ignore rule.
- Each process gets a run tag from the coordinator (D12) and creates `<run-tag>.<identity>.jsonl` there with exclusive creation (`wx`, mode 0600), so two processes on one machine cannot share an identity, and every file names the run it belongs to.
- The file is append-only JSON lines of `{time, id, state}`; each append is followed by `fsync`. If an append or fsync fails, the module throws and the request is not sent.
- States: `allocated` (id handed out), `put-sent` (flushed immediately before every PUT leaves, the first or a later one), `created` (the independent GET returned 200), `delete-sent` (flushed immediately before every DELETE leaves), `deleted` (the independent GET returned 404), and `collided` (terminal: a 404 check found something already at the id). A normal id moves `allocated`, `put-sent`, `created`, `delete-sent`, `deleted`; a later save of the same id goes back to `put-sent`. `collided` has no successor.
- The registry holds ids and states only: no host, no credentials, no cookies.
- It is a crash record, not an authority: a process deletes only ids it holds in memory. No later run reads a registry in order to delete.
- `orphans` (a read-only command over the directory) takes `--run <run-tag>` or an explicit `--all`, and with neither it refuses; it reads only the files of the named run, so it does not list another run's live ids. It lists every id whose last state is `put-sent`, `created`, `delete-sent` or `collided` (it may exist), and separately ids whose last state is `allocated` (never sent). With credentials it also GETs every id that ever reached `put-sent`, including those whose last state is `deleted`, and reports any that exists, so a PUT that landed after its confirmation timed out is still found. On a clean teardown the module writes the same list for its own run to the run output.

**D3. The rule table (one function, used by both enforcement points).** `classify(request, context)` returns allow or abort with a class and a reason. The context holds the allowed origin (the proxy origin for browser requests, the Fusion base for direct ones), the Banana base path and static roots, and the owned ids with their registry states. Rules apply in this order and the first match decides. Everything that no rule allows is aborted.
1. The URL must parse and have scheme http or https. Otherwise abort, class `bad-url`.
2. The origin must equal the allowed origin exactly. Otherwise abort, class `off-origin`. This stops the gist POST and any absolute `solr.server` from leaving the test browser.
3. The path is percent-decoded once and split on `/`. A segment that does not decode, or is empty, `.` or `..`, aborts, class `bad-path` (a single trailing slash is not an empty segment). If any segment, compared case-insensitively, is `update`, `index` or `_update`, abort, class `write-path`. This includes every request whose path ends in `/update` or `/index` and also `/update/json` and a nested `/index`. The stricter rule is deliberate: no live test reads through such a path.
4. `POST /api/ui-logs` aborts, class `telemetry` (the admin UI's client logging; see D8).
5. By method:
   - **GET, HEAD, OPTIONS:** allowed only if the path and query match one row of the read allowlist below, and then subject to D7 for the stream and graph rows. Anything else aborts, class `unlisted-read`. In the table `<c>` and `<p>` (collections and pipelines) are single segments that match `^(_system|system_logs|banana-it-[A-Za-z0-9_.-]+)$`, so the path of a read names only the test's own collections and the system collections the 1.6.30 flow was observed to use. A stream expression names collections of its own in its text, so the path alone does not bound them: D7 requires the first argument of every collection-taking stream function to match the same pattern, allows no bare positional argument after it, and refuses `{!`, backslashes and single quotes in stream values. With those checks, no read the guard allows names another team's pipeline or collection, subject to residual 6 (how Solr tokenises an expression is not verified); `<id>` may be any one non-empty segment.
   - **POST:** allowed only for the login and for `select` (the last row of the allowlist, with the body checks of D7). The login is `POST /api/session` whose query string is empty or is exactly the one parameter `realmName=native` (once, nothing else), and whose content type is `application/json` (the gateway reads the realm from that parameter and requires a JSON content type, `gw:src/main/java/com/lucidworks/cloud/gateway/security/AuthenticationTokenConverter.java:116-130`; the login application sends `?realmName=native`, so the browser's login and the Node client's login are both this rule). A login with another realm, a second parameter, a repeated parameter or another content type aborts. Any other POST aborts, class `unlisted-write`.
   - **PUT:** allowed only if the path is `/api/blobs/<one segment>`, the query string is exactly `resourceType=banana`, there is no fragment, the decoded segment is an owned id, and that id's state is not `collided`. The allow result says whether the 404 check must run first: it may be skipped only when the id's last state is `created` (an overwrite of the test's own dashboard). In every other state (`allocated`, `put-sent`, `delete-sent`, `deleted`) the check runs again before this PUT. A PUT for a `collided` id aborts, class `collided`. Anything else aborts, class `blob-put`. Banana's PUT is only used for saving a dashboard (`src/vendor/solrjs/solr-angular-client.js:93`), so no other PUT is expected.
   - **DELETE:** allowed only if the full request URL string equals `<allowed origin>/api/blobs/<encodeURIComponent(id)>` for an owned id whose state is `put-sent`, `created` or `delete-sent`, with no query string, no fragment and no further segment. A `collided`, `allocated` or `deleted` id aborts. Otherwise abort, class `delete`. The URL is built by one function, `deleteUrl(origin, id)`, which the client and the rule both call (D11). The one other DELETE allowed is the logout: `DELETE <allowed origin>/api/session` with no query string, no fragment, no further segment and no body (`gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewaySecurityConfig.java:203`). It is a different rule from the blob delete, touches no blob, and needs no registry state.
   - PATCH and every other method abort.

The read allowlist. A path is compared after the decoding of rule 3. A query string that a row does not name must be empty. Rows are the routes the 1.6.30 flow was observed to use on the shared instance, plus Banana's own static files.

**D4. The Node client (direct writes).**
- It exposes only: `login`, `logout`, `allocate`, `get(id)`, `create(id, dashboard)`, `remove(id)`. `logout()` sends `DELETE /api/session` for the client's own session through `classify` (the logout rule of D3), without following redirects, and then drops the cookie. Banana has no logout code (`src/app/services/lucidworksSrv.js:15-18`), so a test that exercises logout calls this helper for the Node session, or the browser helper of D5 for the browser's session; specs cannot call `fetch` or `page.request` themselves. `get` accepts only owned ids. It builds the Banana blob document with the same field names Banana uses (`src/app/services/dashboard.js:73` to `src/app/services/dashboard.js:76`), so a direct save looks like a UI save.
- Every direct request is built by the module, run through `classify` with the Fusion base as the allowed origin, and sent with redirects not followed (`redirect: 'manual'`). A 3xx answer is a failure and the request is not repeated at the new address.
- It reads the Fusion base and the credentials from the environment, logs in with `POST /api/session` using the native realm, and keeps the session cookie in memory. The login is the form D3 allows: an empty query or exactly `realmName=native`, with a JSON content type and a JSON body; the client sends `?realmName=native`, like the login application. It sends no `Origin` header. On a 401 answer it logs in again before its next request, and repeats a GET that got the 401 once; it never repeats a PUT or a DELETE inside the same call (a failed write leaves its state at `put-sent` or `delete-sent`, which the teardown retry accepts after the new login). It does not write the host or any credential to the registry, the output or an error message; messages carry the path only.
- One request is in flight at a time per process, so a run cannot become a load test.
- `create(id)`: the id must be owned and not `collided`. Unless its last state is `created`, `GET /api/blobs/<enc id>` must return exactly 404 first. Anything else (200, 204, 400, 5xx or a network error) refuses the PUT and, for an answer that shows something present or unknown, moves the id to the terminal state `collided`; no later PUT or DELETE is allowed for it. A 401 is the exception: it says the session is gone, not what is at the id, so it is "unknown" in a different sense. The client logs in again and runs the check once more; if that also answers 401, the test is aborted with a session error, the PUT is not sent, and the id is not marked `collided` (its state is unchanged). Also, an id whose earlier save was not confirmed (state `put-sent`, because the PUT may have landed) gets a 200 at the next 404 check and becomes `collided`: the run's own blob is then never deleted by the run and is listed as an orphan (residual 17). That is the price of never overwriting what the check finds. Then append `put-sent` and fsync (every PUT does this); PUT with `resourceType=banana`; `GET` again, which must return 200 with a body whose first element has the id; append `created`. Failure at any step throws. A failed confirmation leaves the state at `put-sent`.
- `remove(id)`: the id must be owned and at `put-sent`, `created` or `delete-sent` (the last so that a teardown retry after an unconfirmed delete is allowed); build `deleteUrl`, run it through `classify`; append `delete-sent` and fsync; DELETE; `GET` must return exactly 404 (so the 204 that a directory returns is a failure); append `deleted`. A confirmation that does not show the final state is retried at most twice, 500 ms apart, and then fails the run. The retries wait for the expected final state; they never repeat the write.
- The confirmation GET is independent: it is made by Node with its own session, never through the browser, the proxy or Banana, and with caching off.

**D5. The browser rule set (writes that Banana makes).**
- The live-test fixture creates every browser context itself, from a browser that only the client module launches, and installs one route on it for all URLs. The context is created with service workers blocked. A test cannot obtain a context that lacks the route (D9 enforces this).
- The fixture is built with `test.extend` and overrides the built-in fixtures: `request` and `browser` are replaced by fixtures that throw on use, with a message that names the guarded alternative, and `context` and `page` are replaced by the guarded ones. A spec that asks for `{ request }` or `{ browser }` therefore fails at setup, before it can send anything. Specs must import `test` from the fixture module (D9).
- The built-in `playwright` worker fixture (`playwright/types/test.d.ts` line 8381) is overridden with a **wrapper of the real module**, not with something that throws. Three built-in auto fixtures take `playwright` and run for every test: `_browserOptions` sets `playwright._defaultLaunchOptions`; `_setupArtifacts` reads `playwright._instrumentation`, `playwright._allContexts()` and `playwright.request._contexts`; `_setupContextOptions` sets `playwright._defaultContextTimeout` and `_defaultContextNavigationTimeout` (`playwright/lib/index.js` lines 77-79, 163-164, 196-210, 352-365, 649-650 and 693-694). A `playwright` that threw, or that lacked those members, would fail every test at setup.
  - The wrapper is a `Proxy` over the module object that the client module itself holds. The client module checks that this is the module the runner's own `playwright` fixture would load (the resolved path of `playwright-core` seen from the client module equals the one seen from `playwright`) and refuses to start otherwise, so a context the client module creates is in the `_allContexts()` that the auto fixtures read.
  - It forwards every read and every write to the real module and calls methods with the real module as `this`. That keeps `_instrumentation`, `_allContexts`, `request._contexts`, `_defaultLaunchOptions`, `_defaultContextTimeout` and `_defaultContextNavigationTimeout` working as the runner expects.
  - It throws, with a message that names the guarded alternative, only from: `launch`, `launchPersistentContext`, `launchServer`, `connect` and `connectOverCDP` of `chromium`, `firefox` and `webkit` (each returned as a proxy that forwards everything else); any read of `_android` or `_electron`; and `request.newContext` (`request` is returned as a proxy that forwards everything else, `_contexts` included).
  - A spec that asks for `{ playwright }` gets the wrapper, and each of those calls throws. The wrapper does not hide the real module completely: each browser type carries a `_playwright` back-reference to it (`playwright-core/lib/coreBundle.js` lines 65792-65799), so `wrapper.chromium._playwright` and `page.context().browser().browserType()._playwright` reach the unwrapped module, and `page.context().browser()._newContextForReuse()` (`playwright/lib/index.js` lines 446-449) and the `_channel` of a client object are other internal routes. What stops them is the source check: its tokens match as substrings of identifiers, so `newContext` also catches `_newContextForReuse`, and `_playwright` and `_channel` are tokens of their own (D9). A form hidden from the check is residual 1. The client module is the only code that launches a browser by design (D9). This rests on Playwright internals (residual 16).
  - The guarded browser's worker fixture depends on the runner's `_browserOptions` fixture, so `_defaultLaunchOptions`, including the runner's own `tracesDir` and `artifactsDir`, is set before the guarded launch reads it.
- **Every option key is set explicitly**, because the runner fills any key the creator leaves out.
  - For a context, the runner copies each key of the combined `test.use` options that the creator did not pass (`if (!(key in options))`, `playwright/lib/index.js` lines 122-133), and the combined options include the free-form `contextOptions` object (lines 265-351). For a launch, `launch` and `launchPersistentContext` merge `_defaultLaunchOptions`, which `test.use({ launchOptions })` sets, under the keys the caller passes (`playwright-core/lib/coreBundle.js` lines 65409 and 65423). Left to default, a spec's `test.use` could add a proxy, a stored session, HTTP credentials, extra headers, a browser executable or launch arguments.
  - Context keys, present in every `newContext` call the client module makes: `acceptDownloads`, `baseURL` (the proxy origin), `bypassCSP`, `clientCertificates`, `colorScheme`, `contrast`, `deviceScaleFactor`, `extraHTTPHeaders`, `forcedColors`, `geolocation`, `hasTouch`, `httpCredentials`, `ignoreHTTPSErrors`, `isMobile`, `javaScriptEnabled`, `locale`, `offline`, `permissions`, `proxy`, `reducedMotion`, `screen`, `serviceWorkers` (`"block"`), `storageState`, `timezoneId`, `userAgent` and `viewport`. A key whose Playwright default is wanted is passed present with the value `undefined`, which the runner's `key in options` test counts as set.
  - The fixture also overrides the runner's `_combinedContextOptions` fixture with an empty object, so the free-form `contextOptions` bag, which can hold any key (for example `recordVideo` or `logger`), adds nothing. A spec's own `test.use({ _combinedContextOptions: ... })` would override that override, so the source check refuses the token `_combinedContextOptions` outside the client module (D9). If it were bypassed, only keys outside the explicit list could get through (`logger`, `recordHar`, `recordVideo`, `strictSelectors`, `videoSize`, `videosPath`), and none of them is a network path.
  - Launch keys, present in every `launch` call: `args`, `channel`, `chromiumSandbox`, `downloadsPath`, `env`, `executablePath`, `firefoxUserPrefs`, `handleSIGHUP`, `handleSIGINT`, `handleSIGTERM`, `headless`, `ignoreDefaultArgs`, `logger`, `proxy`, `slowMo` and `timeout` (`playwright-core/types/types.d.ts` lines 25907-26041). `logger` is the one key where "present" is not enough: `launch` and `launchPersistentContext` take `options.logger || _defaultLaunchOptions.logger` (`playwright-core/lib/coreBundle.js` lines 65408 and 65433), so a `logger` of `undefined` would be filled from the spec's `test.use`. The client module therefore passes an explicit no-op logger object (an `isEnabled` that returns false and a `log` that does nothing). A logger is not a network path; the explicit value only keeps the statement "every key is explicit" true. The other two members of that interface, `tracesDir` and `artifactsDir`, are taken from `_defaultLaunchOptions` on purpose: they are the runner's own output directories and name no network target.
  - A unit test compares both lists with the member names of `LaunchOptions` and of the runner's context options in the installed version and fails when a version adds a key that is not listed.
  - So a spec's `test.use` options for the context or the launch (`serviceWorkers`, `proxy`, `storageState`, `httpCredentials`, `extraHTTPHeaders`, `launchOptions`, `contextOptions`, and a replacement `context` fixture) cannot change the guarded context. A spec that replaces `context` in `test.use` still cannot make an unguarded one, because it has no browser to make it from, and D9 refuses the launch and context-creation tokens.
- The request-class guard. `page.request` and `context.request` are one object that carries the session's cookies and that no route sees (`types.d.ts` lines 5866-5873 and 11060-11062), so a spec could alias it. When the fixture starts in a worker it takes the prototype of that object's class and replaces its public methods `fetch`, `get`, `head`, `post`, `put`, `patch` and `delete` with functions that throw and whose message names the guarded alternative. It leaves the internal path intact: `route.fetch` sends through `this._context.request._innerFetch(...)` and does not call the public methods (`playwright-core/lib/coreBundle.js` lines 61223-61264 and 61723-61724), so the write path of this section keeps working. `_innerFetch` is an ordinary method of the same class and stays reachable: `route.fetch` needs it, so it cannot be replaced. D9 refuses the token `_innerFetch`, and a deliberate bypass of that check can still call it (residual 1). Making the `request` property itself throw would break `route.fetch`, so the methods are replaced and the property is left alone. This rests on Playwright internals (residual 16).
- Every WebSocket is closed. The fixture registers `context.routeWebSocket` for all URLs with a handler that closes the socket without connecting it to a server, and records it as an abort. A WebSocket is the admin UI's channel when its URL, with `ws` read as `http` and `wss` as `https`, has the same scheme, host and port as the allowed origin (the proxy's), and its path is exactly `/api-ws` with no query. The admin UI builds that URL from `ws` or `wss` plus the page's own host and port (`fw:app/common/services/web-sockets-service.ts:10-14`), so a comparison with the `http(s)` origin as written would never match. That channel is recorded with class `telemetry`, like the admin UI's client logging: closed, counted, and not a failure. The admin UI reconnects 5 seconds after every close (`fw:app/common/services/web-sockets-service.ts:23-29`), so the telemetry count grows until the page navigates to Banana. Every other WebSocket is recorded with class `websocket`, which fails the test (Banana opens none). The guard does not rely on that fact.
- For each request, the route calls `classify`. An abort is recorded with its class and URL path and the request is aborted.
- **Every allowed request whose method is not GET, HEAD or OPTIONS (login POST, select POST, PUT, DELETE) is sent with `route.fetch({ maxRedirects: 0 })` and never `route.continue`.** A 3xx answer is not passed to the page: the route fulfils the page with an error answer (502 and a short body), records an abort of class `redirect`, and the redirect target is never contacted. Playwright calls a route only for the first URL of a redirect, so a continued 307 or 308 would repeat the method and body at an unchecked address. All other answers are passed to the page with `route.fulfill` from the fetched response, after the steps below.
- PUT: if the allow result requires it (D3), run the 404 check (D4: a 401 makes the Node client log in again and check once more; a second 401 aborts the request and fails the test with a session error, without marking the id `collided`); any other failed check moves the id to `collided`, aborts the request, and fails the test. Then append `put-sent`, send, run the confirmation GET (200), append `created`, and answer the page. A PUT to an id at `created` skips only the 404 check; it still appends `put-sent` and is still confirmed.
- DELETE: append `delete-sent` and fsync before anything is sent, send with `route.fetch({ maxRedirects: 0 })`, run the confirmation GET (404), append `deleted`, and only then fulfil the page with the fetched answer. A confirmation that fails is recorded as a debt that fails the test (D10). The page is not told, because Banana would report success whatever the answer was (`src/app/controllers/dashLoader.js:170`). The logout DELETE (D3) has no registry state and no confirmation; it is sent with `route.fetch({ maxRedirects: 0 })` like every other write. Banana has no logout code (`src/app/services/lucidworksSrv.js:15-18`), so the browser's logout is issued by a helper of the client module, `logoutBrowser(page)`, which runs `fetch('/api/session', { method: 'DELETE' })` inside the page. That request goes through the context route with the browser's own cookie and meets the same rule. Specs call the helper and never `fetch`; the admin UI's logout button is not used, because tests avoid the admin UI (D8).
- GET, HEAD and OPTIONS that pass the allowlist are continued unchanged. A redirect hop of such a request is not seen by the route, so the fixture also listens to the context's request events and, for every hop that carries a `redirectedFrom`, runs `classify` on it afterwards. A hop that classify would abort fails the test (detective, not preventive; residual 12).
- All writes of one process go through one queue, so PUTs of the same id are serialised and the state each one sees is current.

**D6. Start-up check of the mode.** Before a context is created, the fixture fetches the served `config.js` from the Banana base URL it was given, evaluates it in an isolated `vm` context with stub `define` and `Settings` (no network, no `require`), and refuses to start unless `USE_FUSION` is true and `SYSTEM_BANANA_BLOB_API` is `/api/blobs`. The same values are the shipped defaults (`src/config.js:67`, `src/config.js:75`). If the check fails, nothing is sent to Fusion. The check cannot see a later switch; the rule table covers that case (S7). The fixture also performs the instance check of D12.

**D7. Stream, graph and select requests.** These are the only requests whose content decides whether they are reads, so they have their own checks, applied after the path rows of D3.
- Stream and graph (GET): the query string must consist of exactly one parameter, `expr`, once and non-empty. Any other parameter aborts (so a string appended by the timeseries panel's custom field aborts), as does an empty or repeated one. A `$` anywhere in the raw query string or in the decoded value aborts, class `stream-write`; the test applies to decoded values because Banana sends `$` as `%24` (`src/app/services/querySrv.js:115`) and a raw-only test would miss it; this refuses Solr's `${name}` parameter substitution without having to know whether Solr performs it. The value is decoded once like a form value (`+` as space, then percent-decoding as UTF-8); a value that does not decode aborts, and a decoded value that still contains a percent sign followed by two hexadecimal digits aborts as doubly encoded. The decoded value must not contain `{!` anywhere, inside double quotes included, the same refusal that select applies to every value that the table does not give the two exact prefixes (Banana builds no `{!` in a stream expression); it aborts, class `stream-scope`. That refuses `{!join fromIndex=<other> ...}` and every other local-parameters query parser, which can name a collection or a handler from inside a `q` or `fq` string. A backslash or a single quote anywhere in the decoded value aborts too, class `stream-scope`: Banana's templates emit neither, and refusing them means the scan below does not depend on how Solr treats escapes or single quotes.
- Note (2026-11-07): since the stream-expression panels were changed to quote their values, they do emit escaped double quotes (`\"`) for a terms filter value, a phrase in a query or any value that contains a double quote, and an apostrophe is also written as is. This check refuses those requests, so a live run uses stream panels on dashboards without such filters or queries. It fails closed.
- The expression is scanned outside double-quoted strings. Because a backslash and a single quote are already refused, a double quote always starts or ends a string, with no escape forms to model. Brackets (round, square and curly) and quotes must balance, or the request aborts, class `stream-scope`.
- A function name is the run of characters that are not whitespace, control characters, `(`, `)`, `,`, `=`, quotes, brackets or braces, that is followed, after optional whitespace of any kind, by `(`. So `update(`, `update (` and `update` followed by a tab or newline and `(` are all names. Every name must be exactly (case-sensitive) in a fixed set: `search`, `nodes`, `fetch`, `select`, `significantTerms`, `timeseries`, `facet`, `stats`, `random`, `sort`, `top`, `count`, `sum`, `avg`, `min`, `max`, `rollup`. These are the functions the panels build (`src/app/panels/graph/module.js:117`, `src/app/panels/significantTerms/module.js:114`, `src/app/panels/timeseries/module.js:177`) plus the plain aggregation functions. A name outside the set aborts, class `stream-write`.
- Collections. A stream expression names the collection it reads as its first positional argument, so the path of the request does not bound it: Banana itself sends `nodes(<collection of the graph panel>, ...)` with a dashboard-configured collection (`src/app/panels/graph/module.js:117-118,130`), and a stream expression can read any collection the user can read. For every occurrence of `search`, `nodes`, `fetch`, `facet`, `stats`, `random`, `timeseries` and `significantTerms` (every function of the closed set that takes a collection), at any depth, the first argument, taken as the text between the opening `(` and the first `,` or `)` outside double quotes and brackets, with surrounding whitespace removed, must be a bare token that matches `^(_system|system_logs|banana-it-[A-Za-z0-9_.-]+)$`, the same pattern as `<c>` in the path (D3). A quoted first argument (`"name"`), an empty one, one with an inner space, a nested function call, a named argument (`collection=...`) or a name outside the pattern aborts, class `stream-scope`. The scan finds every occurrence by the function-name rule above, so a source stream nested inside another function (`fetch(c, search(c2, ...), ...)`, `top(n=3, search(c2, ...), by=...)`) is checked the same way, recursively. No later argument of a collection-taking function is a bare positional token: each is a named argument (`name=...`) or a call of a function of the set, and anything else (for example `search(c, other, q=...)`) aborts, class `stream-scope`. `select`, `sort`, `top`, `count`, `sum`, `avg`, `min`, `max` and `rollup` take streams or tuples, not a collection, so their first argument is not checked as one; whatever stream they wrap is. The first argument is not required to equal the path's collection, only to be a permitted one. This is why a graph panel's `graph_collection` has to be a permitted collection under test (Costs).
- Named arguments. Inside the expression, every argument name must be in the stream argument allowlist. An argument name is an identifier (the same character class as a function name) outside double-quoted strings, followed after optional whitespace by `=`. The allowlist is `q`, `fq`, `fl`, `sort`, `rows`, `field`, `limit`, `minDocFreq`, `maxDocFreq`, `minTermLength`, `walk`, `gather`, `scatter`, `trackTraversal`, `on`, `start`, `end` and `gap`. These are the named arguments the panels build: `q` and `fq` (`src/app/services/querySrv.js:115`, `src/app/services/filterSrv.js:283`, `src/app/panels/significantTerms/module.js:111-115`, `src/app/panels/timeseries/module.js:224`), `field`, `limit`, `minDocFreq`, `maxDocFreq` and `minTermLength` (`src/app/panels/significantTerms/module.js:115-117`), `fl`, `sort`, `rows`, `walk`, `gather`, `scatter` and `trackTraversal` (`src/app/panels/graph/module.js:117-136`), `fl` and `on` of the label lookup (`src/app/panels/graph/module.js:151`), and `field`, `start`, `end` and `gap` (`src/app/panels/timeseries/module.js:245-248`). Any other name aborts, class `unlisted-param`.
- A name that has `shards` or `qt` as a dot-separated component (compared case-insensitively) aborts, class `refused-param`, in every position: `shards`, `shards.qt`, `x.shards`, `qt` and `x.qt`. The rule applies to the argument names of every function in the closed set, so `shards="..."` inside `facet(...)`, `stats(...)` or `timeseries(...)` is refused like any other unlisted name. Banana never sends `qt`, so no value of it is allowed; `qt="/select"` is refused too. `zkHost` is not in the allowlist and aborts as an unlisted name. The functions in the set that Banana never builds (for example `facet`, `stats`, `random`, `top` and `rollup`) can therefore be used only with the arguments above. Argument values are not parsed, beyond the `$` and `{!` tests, the quote balance, the double-encoding test and the first-argument rule above.
- Select (POST): the request's content type must be exactly `application/x-www-form-urlencoded` (what Banana sends, `src/vendor/solrjs/solr-angular-client.js:70`), compared case-insensitively, with no parameter except an optional `charset=UTF-8`; any other parameter or charset aborts, so Solr cannot decode the body in a character set other than the one the guard used, and Solr's JSON request body is refused. The URL has no query string (a `select` URL never carries one in Banana's panels). The body is split on `&`; each pair is a name and a value, each decoded once like a form value (`+` as space, then percent-decoding as UTF-8). A name or a value that does not decode as UTF-8 aborts (class `unlisted-param` for a name, `bad-param-value` for a value). A pair with an empty name, a name that does not decode, or a decoded name that still contains a percent sign followed by two hexadecimal digits aborts, class `unlisted-param`. Then, in this order:
  1. A `$` in the raw body or in any decoded value aborts, class `select-write` (Solr's `${name}` substitution).
  2. A name that has `shards` or `qt` as a dot-separated component (case-insensitive) aborts, class `refused-param`, even where the name belongs to an allowed family: `shards`, `shards.qt`, `x.shards`, `qt`, `x.qt` and `f.qt.facet.limit` all abort. A field that is really called `shards` or `qt` therefore aborts a read; that is the price of a rule that needs no Solr knowledge.
  3. A name that is not in the parameter allowlist below aborts, class `unlisted-param`. This is deny-by-default, not a list of known-bad names: `expr`, `stmt`, `stream.*`, `collection`, `distrib`, `start`, `echoParams`, `debug`, `json.*`, `tr` and every handler-switching, routing or logging parameter that nobody thought to name are refused for the same reason, that Banana does not send them.
  4. A value that does not match the shape the table gives for its name aborts, class `bad-param-value`. The `{!` of a Solr local-parameters prefix is allowed only where the table says so (the two exact prefixes Banana builds); in every other value, `{!` aborts.

**D9. A source check that backs the claim "only path".** A check script (run by `npm run test:live` before Playwright starts, and by a unit test over the real tree) scans every `test/live/**` source file, and the `test:live` entries of `package.json`, except the client module `test/live/fusion-client/**`. The client module is the only place where a context or a browser is created, a process is started, or a request is made, and it is the only code that the check does not scan; it has its own unit tests and is reviewed as guard code. The check refuses:
- Imports that bring in Playwright's own `test` or `request`. Outside the client module, a file may import from `@playwright/test` only `expect` and type-only names (`import type`). It refuses any other named import, a default or namespace import, `require('@playwright/test')`, a dynamic `import()` of it, and any import or `require` of `playwright` or `playwright-core`. It also refuses a `*.spec.*` file that does not import `test` from the fixture module. Together with the fixture's throwing `request` and `browser` (D5), a spec cannot reach the stock `page`, `context`, `browser` or `request`.
- The tokens `newContext`, `newPage`, `.connect`, `.launch`, `launchPersistentContext`, `launchServer` and `connectOverCDP`, because a context or browser made this way has no guard (this covers `browser.newContext`, `page.context().browser().newContext`, `browserType.connect` and the rest), and `.extend` and `mergeTests`, which could put a stock fixture back. Tokens that end in a call are matched with optional whitespace before the parenthesis (`.connect (`, `.launch (`, `.extend (` and `got (` are the same as the compact forms).
- The tokens `newCDPSession` and `newBrowserCDPSession` (a DevTools session can open a page in a context that Playwright does not route), `_innerFetch` (the internal request method that `route.fetch` uses and that the replaced public methods leave in place), `_android` and `_electron`, `_playwright` (the back-reference from a browser type to the real module that the `playwright` wrapper wraps), `_channel` (the protocol channel of a client object) and `_combinedContextOptions` (the runner fixture that the guarded fixture overrides, which a spec's `test.use` could override again). Tokens match as substrings of identifiers, not only as whole words, so `newContext` also catches `_newContextForReuse`, and `_playwright` also catches `chromium._playwright` and `browserType()._playwright`.
- The bare identifier `fetch` in any position (so `const f = fetch`, `fetch (` and `globalThis.fetch` all fail, not only `fetch(`), and `XMLHttpRequest`, `sendBeacon`, `axios`, `undici`, `node-fetch` and `got`;
- Any `.request` property access that is not a call (`page.request`, `context.request`, `?.request`, `['request']`), so `const api = page.request` fails and `.request.` is only one case of it; any object destructuring pattern, in a declaration or in a parameter list, that names `request` (so `const { request } = page.context()` fails); and `request.newContext` and `APIRequestContext`. The fixture's replacement of the request methods (D5) backs this check when the check is bypassed;
- `http.request`, `https.request` and `require` or `import` of `http`, `https`, `http2`, `net`, `tls`, `dgram` and `child_process`, in the plain form and in the `node:`-prefixed form (`node:https`, `node:net` and the others);
- `curl` and `wget` in a script or a `package.json` entry;
- `.route(`, `.unroute`, `.unrouteAll`, `routeFromHAR`, `routeWebSocket`, and `route.continue(` with an override (again with optional whitespace before a parenthesis). A page-level route whose handler continues a request skips the context route, so a test must not register its own.
- The client module's internals by name: `_session`, `_guard`, `_guardedBrowser`, `_once`, `_fetch` (as substrings) and a `.ledger` member access. A spec has no use for them, and they would let it send an unchecked request or put another run's id into the ledger.
- An import of `defineConfig` from Playwright and any Playwright configuration file outside the client module. The Playwright configuration lives inside the client module (the `test:live` command passes it to Playwright with `--config`), so the scanned files never need that import.
The check also fails if the fixture's own file no longer contains the route installation, the WebSocket route, the wrapper of `playwright`, the overrides of `request`, `browser` and `_combinedContextOptions`, the explicit context and launch key lists, the no-op logger, the dependency of the guarded browser fixture on `_browserOptions`, or the replacement of the request-class methods (a test of the check), and it refuses to start unless the installed Playwright version equals the version pinned in `package.json`, which is 1.65.0 (an exact version, no range), and, where a local lockfile exists, the version in that lockfile. `package-lock.json` is ignored by git in this repository, so the lockfile comparison runs only on a machine that has generated one, until a lockfile is committed. The check is a tripwire for honest mistakes, not a sandbox (residual 1 below). The code that starts the proxy container, and so uses `child_process`, lives in the client module (D12); the `test:live` entry is one command that runs the client module's launcher.

**D10. Failure policy.**
- An abort of any class other than `telemetry` (and an off-origin GET or HEAD) fails the test at its end, and the test output lists the aborted method, class and path. A refusal is never silent.
- A confirmation debt (D4, D5) fails the test.
- A collision (the 404 check does not return 404 for an id, on the first PUT or on a later one) fails the test with the id. The id moves to the terminal state `collided`: every later PUT or DELETE for it aborts, so a second save of the same title cannot overwrite what the check found, and no delete is ever attempted for it. No replacement is chosen automatically.
- At worker teardown, the module removes each owned id at `put-sent`, `created` or `delete-sent`, using `remove`; `collided` ids are skipped and reported. An id that stays at `delete-sent`, whose confirmation showed it still exists, is retried once and then reported as an orphan, and the run fails.
- If the process dies, nothing runs; the registry is the record (D2). A worker that crashes leaves its ids as orphans even though the run continues: only the process that created an id can delete it.
- The orphan list for the run is written to the run output so that the owner can delete the blobs by hand.

**D11. The delete URL form, and who may change it.** The delete form of D3 is the form Banana sends today for a plain id: origin, `/api/blobs/`, the encoded id, no query. The later design record for the save and delete change fixes the delete URL that Banana will send. That record, and the change that implements it, must update `deleteUrl` and the unit tests that pin it in the same change; the rule here follows it. If the two disagree, deletes fail closed (they are aborted and the id is reported), which costs orphans and never a wrong delete.

**D12. One run tag, one instance.**
- The coordinator is a launcher inside the client module (`test:live` is one command that runs it). It runs the source check (D9), issues a random 12-hex-digit run tag once per invocation, exports it to the workers it starts, starts the proxy container, and then starts Playwright. Code that starts a container, and so uses `child_process`, lives only in the client module. A process that finds no valid run tag in its environment refuses to start, so a spec run directly with `npx playwright test` fails before sending anything.
- One environment variable (indicative name `BANANA_LIVE_FUSION_URL`) gives both the proxy's upstream and the client's base: the launcher passes it to the proxy and the client reads it, and there is no second setting. This prevents the 404 check and the confirmations from reading one instance while the browser writes to another.
- The instance check uses a digest header that exists only for tests. The launcher draws a random 32-byte key once per invocation (indicative variable name `BANANA_LIVE_DIGEST_KEY`) and passes it to whichever container it starts, whether the test proxy or a hosting image, and to the fixture. A container emits the header (indicative name `X-Banana-Upstream-Digest`) on its responses only when that variable is set, and the value is the HMAC-SHA-256 of its upstream origin under that key. The fixture computes the same HMAC of its own base, compares it on its first request through the proxy, and refuses to start on a mismatch, a missing header (a proxy the launcher did not start) or an unset variable. Because the key is new for each run and is never written to the registry, the output or a log, a header recorded in a log does not reveal or confirm the host name.
- This is a test-only contract that any container image the launcher may start must keep: **the container image must not emit the header unless the key variable is set**, and the variable is unset by default in every image, so an image that ships to users carries no such header and no change of default. Whatever design later hosts Banana in a container keeps that rule, and so does every image built from it (Consequences lists it as a constraint on later work); if a hosting image cannot or does not implement the header, the launcher refuses to run against it rather than weakening the check.
- The test proxy forwards only `/api`, `/auth/` and `/admin/` (not `/admin/banana/`) to the instance and serves Banana's files itself. This change adds the test proxy itself (under `test/live/proxy/`, started by the launcher), because the browser leg of the acceptance run needs it and cannot wait for a hosting image. The proxy implements the header and this split, and its tests pin them.

**Why each guard is a no-op on a normal run.** A normal run uses only ids from `allocate`, saves each once, deletes each once through the exact form, reads with GETs, posts queries to `select` (only parameter names that Banana's own code sends, all in the D7 table), logs in once per browser session or Node session (a `POST /api/session` with `realmName=native`, which the login rule allows; the browser helper repeats a click only when no login request was seen, never a request that was sent) and logs out at most once, through the client module's helper. None of those is refused. The runner's own auto fixtures run unchanged against the `playwright` wrapper. The browser login lands either on the Banana page or, if the login application ignores the return address, on the admin UI; the fixture then navigates to Banana in both cases (D8). The admin landing's reads, `GET /api-ws` among them, are on the allowlist, so they pass. The aborts that do occur on a normal run are the admin UI's telemetry, `POST /api/ui-logs` and a WebSocket to `/api-ws`, which are counted and ignored; a normal run that lands on Banana has none. Whether the login application honours the return address, and whether the admin landing makes any other call that no row names, is shown only by the live run. The start-up check passes on any build that ships the Fusion defaults. In Solr mode no write reaches Fusion: save and delete are refused (D3 rule 3), and reads still go through the allowlist.

## Consequences

Better:
- Rule 9's "delete only blobs this run created, through the guarded client" is enforced for Node code and for Banana's own UI, and a failed or mis-aimed delete can no longer pass as a success.
- A crash leaves a complete list of what may remain on the shared instance.
- The tests can exercise Banana's real delete path without being able to hurt the shared instance.

Costs and behaviour changes:
- Live tests are slower: each id costs at least three extra GETs, and the browser waits for the confirmation before it sees the response. Ids are only plain `banana-it-<identity>-<n>` titles, so odd-title behaviour is shown by unit tests of the save and delete code, not live.
- Tests may not open their own contexts, register routes, call `fetch` or touch `page.request` in any form (including an alias or a destructured `request`); they go through the fixture, whose `request` and `browser` throw, whose `playwright` is a wrapper that throws only from the calls that launch or connect a browser, from `_android`, `_electron` and `request.newContext`, and which replaces the public methods of the request class. The source check enforces it. The Playwright configuration lives inside the client module. Logout is issued by helpers of the client module, not by specs.
- Reads are limited to an allowlist of routes. A test that needs another read route adds a row and a unit test; a dashboard whose panels or dashboard-wide extra parameters use `qt`, a `$` or a stream parameter other than `expr` aborts under test. Specifically:
  - A table panel with "calculate top values from all data" sends a GET `select` (`src/app/services/solrSrv.js:34-41`), which has no row, so it aborts and fails the test; the fixture dashboard keeps that option off.
  - A non-empty dashboard-wide `global_params` is appended to every query, stream `expr` strings included (`src/app/services/querySrv.js:115-133`), so its stream panels abort as extra parameters; the fixture dashboard keeps it empty. The bundled dashboards that set it (`src/app/dashboards/default.json` (line 674 at the integration head), `src/app/dashboards/guided.json:362`, `src/app/dashboards/syslog.json:322`, `src/app/dashboards/lucidworks-service-logs.json:674`, `src/app/dashboards/lucidworks-combined-logs.json:1516`, `src/app/dashboards/lucidworks-access-logs.json:809` and `src/app/dashboards/lucidworks-searchanalytics.json:1313`) have no stream panel, but they would abort if one were added.
  - Select bodies may carry only the parameter names of the D7 table, with values of the stated shapes. A dashboard whose `global_params`, or a panel whose custom query string, carries any other parameter aborts under test: `qt` or `shards` (class `refused-param`), `collection`, `start`, `mm`, `echoParams` or `defType=xmlparser` (classes `unlisted-param` and `bad-param-value`), and `{!` in a `q` or `fq` value. The bundled dashboards' extra parameters (`df` and `fq`) are inside the table. A test that needs another parameter adds a table row and a test.
  - A dashboard with an index interval set makes Banana call `src/app/services/kbnIndex.js:120`, a GET `select` that has no row, so it aborts; the fixture dashboard leaves the interval unset.
  - Reads of pipelines and collections other than `_system`, `system_logs` and `banana-it-*` abort, in the path and, for a stream expression, in the first argument of every collection-taking function (D7). The invariant holds under residual 6: an expression whose tokenisation by Solr differs from the scan's is the one thing not shown.
  - A graph panel's `graph_collection` (`src/app/panels/graph/module.js:117-118,130`) must be a permitted collection under test: `_system`, `system_logs` or a `banana-it-*` collection. The fixture dashboard sets it so; a dashboard that names another collection aborts as `stream-scope`.
  - A `{!` anywhere in a stream value aborts, so a stream panel whose `q` or `fq` holds a local-parameters prefix aborts under test.
- A redirect answer to a write is turned into an error answer, so a test cannot follow one.
- The only writes besides blob saves and deletes are the login and the logout; a test that needs another kind of write needs an explicit rule and a record.
- The digest header is a test-only contract (D12): a container the launcher starts must not emit it unless the key variable is set, and this change adds the test proxy that implements it.
- The first run after this lands has no prior state: it needs the registry directory (untracked and ignored, or outside the work tree) to exist, and the Fusion URL and credentials in the environment. Playwright is pinned to one exact version.
- Nothing in `dist/` changes. No release note is needed.

Constraints on later work:
- The digest header is a test-only contract that the later design for hosting Banana in a container, and every image built from it, must keep (D12). The image emits the header (indicative name `X-Banana-Upstream-Digest`) only when the key variable (indicative name `BANANA_LIVE_DIGEST_KEY`) is set, and the variable is unset by default, so a shipped image sends no header that derives from its upstream and no default changes. The header value is the HMAC-SHA-256 of the upstream origin under the key and nothing else. An image that does not implement it cannot be used for the live browser leg: the launcher refuses it rather than skipping the check.
- The delete URL form (D11), the function set, the stream argument allowlist and the select parameter table each change only together with their tests.

### What the first runs showed

The local-browser tests (Playwright 1.65.0 with Chromium, local servers, no Fusion) showed the Playwright behaviour that the typings do not state:
- With `serviceWorkers: "block"`, `register()` still resolves, but the browser then has no registration, no worker and no page controlled by one, so no worker can answer a request before the route sees it.
- A 307 and a 308 answer to a login POST, a select POST, a PUT and a DELETE each come back to the page as 502 with an abort of class `redirect`, and a server standing for the unchecked address received no request: `route.fetch({ maxRedirects: 0 })` returns the 3xx answer instead of following it.
- `route.fetch` sends the context's cookies, and a `Set-Cookie` in a login answer passed to `route.fulfill` reaches `context.cookies()`.
- `page.request` is the same object as `context.request`. After the replacement of the class's public methods every one of them throws and names the guarded alternative, and `route.fetch` still sends the guarded PUT and DELETE in the same run.
- The context's `request` event fires for the redirect hop of a GET, and the hop check reported a hop that the table would refuse.
- A WebSocket a page opens is closed (the page sees the close); `/api-ws` on the allowed origin is counted as telemetry and any other fails the test.
- Through the real test runner: a plain guarded test passes with the runner's auto fixtures running and its context is among `playwright._allContexts()` seen through the wrapper; a spec that asks for `request` or `browser`, or replaces `context`, fails at setup; the options a spec sets with `test.use` (service workers, a proxy, a stored session, credentials, extra headers, a user agent, launch options with a proxy, an executable path, arguments and a logger, and a context options bag with a video setting) reach neither the launch nor the context, because every key is present in each call; the launch receives the explicit no-op logger and the runner's own trace and artifact directories from its defaults; a recorded abort fails the test at its end with its class and path; a proxy that answers with another instance's digest, or serves the Solr preset, and a missing or malformed run tag, each stop the run before anything reaches the instance, the login included.
- A drift test scans the panels and services for the parameter names they build. Every one is in the select table, is a stream argument, or is one of four explained non-select names.

The live run on the shared instance (Fusion 5.9.16, the 1.6.30 `dist/` served under `/admin/banana/` by the test proxy, the guarded client only) passed:
- Two ids were created, each after a 404 check, verified by an independent GET, and deleted with a confirming 404; one of them was saved a second time first, which replaced the body (own id only). One id was saved through Banana's Save screen, reopened, and deleted through the Load screen, with the same independent confirmations. The teardown found nothing left to remove, and `orphans` listed nothing for the run.
- Both logins were `POST /api/session` with the query `realmName=native` and the content type `application/json`, answered 201, so the exact login rule matches the real flow. The login application honoured the return address: the browser landed on Banana, made no request to the admin UI and no telemetry call. One GET to another origin (an icon font that the login application loads) was aborted and counted, which is not a failure.
- A save is `PUT /api/blobs/<id>?resourceType=banana` answered 200, and the confirming GET answers 200 with a JSON array whose first element has the id.
- The blob service accepts the delete URL form of D3: `DELETE /api/blobs/<id>` with no query answered 204, both from the Node client and from Banana's own Delete button (which sends the content type `text/plain;charset=UTF-8` and no body); the GET afterwards answered 404.
- Logout is `DELETE /api/session` with no query and no body, answered 200, for the browser session and for the Node session.
- The dashboard sent 18 select POSTs from 20 panel controllers. All passed the select table, and all were answered 200.

Not shown live: the 204 that a directory answers (as a read only), because the guard allows reads of run ids only through the client and no run id is a directory; and a run killed part way, because that leaves a blob that no later run may delete. The registry file that a killed process leaves, and the `orphans` listing built from it, are shown against the stand-in server only.
