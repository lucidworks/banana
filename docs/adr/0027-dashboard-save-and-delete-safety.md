# 27. Saving and deleting a dashboard cannot overwrite or delete the wrong one

Date: 2026-11-07
Status: Accepted

<!-- This ADR is committed to the repository. It is written for an outside reader. -->

## Context

### Problem

A saved dashboard is stored under its title. In Fusion mode the title is the blob id; in Solr mode it is the document id. The code that saves, loads, lists and deletes handles that id in four different ways, and none of them checks what is already stored. The effects on live data:

- **Saving under a title that exists replaces the stored dashboard without a word.** The blob store accepts a second write to an id with no conflict and keeps no earlier version. A user who types a title that someone else already used destroys that person's dashboard, and neither of them is told.
- **Deleting in Solr mode is a delete-by-query built by string concatenation.** The title goes into `id:"<title>"` and into an XML body unescaped. A title such as `x" OR title:"*` turns the delete into "delete every saved dashboard". A title with `<` or `&` makes the XML invalid, so the delete fails.
- **In Fusion mode save encodes the id and load and delete do not.** A title containing `?` or `#` is saved under its full text but loaded and deleted under a shorter id, so Delete can remove a different dashboard from the one the user clicked.
- **The saved-dashboard list drops the first character of any id that contains `/`.** The Delete button on such a row sends a delete for a different id, which may be a real dashboard.
- **The Solr-mode load query has the same injection as delete.** The id (which AngularJS decodes from the address) goes unencoded into `q=title:"<id>"`, so an id can inject `&` and `#` into the request.
- **The owner recorded with a dashboard is not the logged-in user.** It is whatever `username` the dashboard JSON already carried (every dashboard Banana has saved carries `guest` or the previous saver), or `guest` when the session lookup had not finished. Nothing shows who saved a dashboard that is about to be replaced.
- **Load reports its own failures badly.** The response transformer reads `response[0]` or `docs[0]` and throws on an error body, an empty body (a 204) or an empty result, so the error handler receives an exception instead of the response.

All of these exist in 1.6.30, the version Fusion 5.9.16 ships (see "Behaviour of the last release").

A design constraint follows from how the save works. The write goes through `window.sjs.client`, one global object whose server and mode are re-pointed by every panel query, every refresh timer tick and every `sjsResource()` call. Today the save sets the client's server and writes in the same synchronous turn, so nothing can intervene. A save that first looks up what is stored, waits for the user and looks again has asynchronous steps in between, and the write must not rely on state that was set before them.

### Behaviour of the last release

Read with `git show 76a7d3f:<path>`. Everything below is unchanged on the current branch unless noted.

- **Save** (`rel:src/app/services/dashboard.js:376-449`). The id is the title (`:385`). The blob id is `encodeURIComponent(id) + '?resourceType=banana'` (`:412`). There is no check for an existing dashboard; the PUT or POST goes straight out. The owner is `self.current.username` (`:380`), set from the session once, asynchronously (`:77-79`), and otherwise taken from the dashboard JSON. After a save, `$location.url('/dashboard/solr/' + title)` is called with the raw title (`:420`, `:423`).
- **Load** (`rel:src/app/services/dashboard.js:326-373`). Fusion requests `BLOB_API + '/' + id` unencoded (`:334`). Solr requests `q=<titlefield>:"<id>"` unencoded (`:329`). The transformer reads `response[0]` or `response.response.docs[0]` (`:344`, `:347-350`).
- **Delete** (`rel:src/vendor/solrjs/solr.js:9027-9029` and `:9034-9036`). Fusion: `DELETE BLOB_API + '/' + id`, unencoded. Solr: a GET of `/update?commit=true&wt=json&stream.body=<delete><query>id:"<id>"</query></delete>`, unencoded. Solr 7 and later disable `stream.body` by default, so on those versions the 1.6.30 delete did nothing. The development line before this work changed the request to a POST of the same XML delete-by-query, which Banana's users have never had in a release.
- **List** (`rel:src/app/services/lucidworksSrv.js:73-80`, `rel:src/app/controllers/dashLoader.js:324-325`, `rel:src/app/partials/dashLoader.html:84`). The filter text is encoded; the result is sorted by a `name` field that blob entries do not have; an id that contains `/` loses its first character (the code was written for listings whose ids begin with `/`, and the 5.9.16 listing's `id` does not); the load link contains the raw id. A 1.6.30 client therefore shows, opens and deletes `b/c` for a stored `ab/c`.
- **Owner** (`rel:src/app/services/lucidworksSrv.js:20`). `session.user.username`; `undefined` for a session without one.
- **Co-existence.** Fusion 5.9.16 serves 1.6.30 itself against the same blob store that a newer Banana would use. Both versions are in use together, permanently, not only after a rollback. Dashboards are stored as the same document, under the same id, by both. This record does not change the stored format.

Each residual below says whether 1.6.30 shares it.

## Options considered

1. **Leave the behaviour and document "use plain titles".** Rejected: one mistyped title destroys another user's dashboard, and a crafted one can empty the Solr collection. A convention checks nothing.
2. **Make the blob store refuse a second write (create-only), and send overwrites with a precondition.** Rejected for now: nothing in the pinned sources or the live probe shows that the blob API supports it (see the facts above), and the live-test client's PUT rule does not allow extra headers. It is the preferred remedy for the race and is listed as the follow-up probe.
3. **Check, ask, then write (chosen).** Not atomic, but it removes the silent overwrite for every ordinary case and narrows the remaining window to one request. It is what Fusion's own blob screen does.
4. **Always refuse an overwrite.** Rejected: re-saving one's own dashboard after editing it is the normal way to use Banana.
5. **Skip the confirmation when the stored owner is the current user.** Rejected: in an API-key session, in Solr mode and behind a proxy that signs every request with one account, every user is the same name (`guest` or the shared account). It also fails with real logins after any 1.6.30 save, because 1.6.30 keeps the previous saver's name from the loaded JSON: a user re-saving a stale copy over someone else's 1.6.30 edit would get no dialog. The exemption would turn the protection off where identity is weakest.
6. **A setting that turns the confirmation off (`confirm_overwrite: false`).** Rejected: a switch that restores the silent overwrite is a documented way to lose data, and the confirmation is cheap for the person who saves.
7. **Solr delete as XML delete-by-id with the id escaped.** This was the first draft of this design. Rejected in favour of JSON because the escaping would be hand-written, and a hand-written escaper is the kind of defect this record removes. XML 1.0 cannot carry some control characters even when escaped, and whether Solr trims the text of `<id>` is unverified. JSON delete-by-id has no query syntax at all, `JSON.stringify` does the escaping, and the save already sends JSON to the same `/update` handler with the same parameters, so the endpoint is proven wherever saving works. If the maintainers prefer XML, the fallback is `<delete><id>…</id></delete>` with `& < > " '` escaped and control characters refused.
8. **Keep Solr delete as delete-by-query and only escape the quotes.** Rejected: a query parser has more special characters than any escaper should be trusted with, and delete-by-id is exactly what is meant.
9. **Load Solr dashboards by the `id` field instead of the title field.** Rejected for load: 1.6.30 matches on the title field, and changing the field could miss a document whose id differs from its title. The overwrite check uses `id`, because a Solr overwrite replaces the document with that unique key.
10. **Refuse every title with `/` in it.** Rejected: 1.6.30 stores such titles and the blob store accepts them (observed live). They can be made to work end to end in this client, as set out in rule 8, though a 1.6.30 client still mishandles them (see the residuals).
11. **Encode the id once in the hash link.** Rejected: AngularJS 1.0.8 decodes it before matching the route (see the facts), so `/` splits the route. The link encodes the id twice and the route decodes once more.
12. **Ask for confirmation with an in-page dialog instead of `window.confirm`.** Rejected: the delete button already uses `window.confirm` through the `confirm-click` directive, and one mechanism is easier to test and to reason about.
13. **Write through the shared `sjs.client` after the asynchronous steps without re-setting it.** Rejected: see the Problem; a refresh tick can re-point it.
14. **Make every save write through `$http` with the URL captured at the start, bypassing the shared client.** Not chosen. It removes the shared state entirely, but it would duplicate the body building that `doIndex` and `doDelete` own and that the recorded-response tests and the live-test client already exercise. The chosen way keeps those two functions and sets the shared client's server and mode in the same synchronous turn as the call, after the last asynchronous step, from values captured at the start. A test pins that order (rule 3).
15. **Send `_version_` with a Solr overwrite for real optimistic concurrency.** Not adopted. Solr's `_version_` is larger than 2^53, so `JSON.parse` in the browser rounds it and the value cannot be sent back unchanged; the body would need the digits spliced in as text. A first save cannot send `-1` without knowing that the collection's schema has the field, and a schema without it would then refuse every save. Neither can be tested without a live Solr, which plain Solr support does not include (ADR 7). The lookup still reads `_version_` and uses it for the recheck. Real optimistic concurrency is the remedy named in the residuals.
16. **Use HEAD before GET for the existence check.** Not adopted. The lookup needs the stored owner and body, so a GET follows a 200 anyway, and a HEAD has no body from which to check that a 404 is the blob store's own "no such blob" answer. The cost is that a GET of a large non-Banana blob under the same name downloads it once, on a collision.

## Decision

The confirmation on overwrite (option 3, with options 4 to 6 rejected) was decided by the project owner on 2026-11-07: always confirm, with no setting. It applies in both modes, to every overwrite, including a user's own dashboard.

Rules apply to both hosting modes unless a mode is named.

**Rule 1: one codec for the Fusion blob id.** Every request that names a stored dashboard in Fusion mode (the existence check, load, save, delete) builds its URL from the same function: `SYSTEM_BANANA_BLOB_API + '/' + encodeURIComponent(id)`. The save adds the query `resourceType=banana` after it, as 1.6.30 does. `doDelete` encodes in its Fusion branch (the id is passed raw today) and `doIndex` keeps receiving the encoded blob id from `dashboard.js`. One unit test builds the four URLs for each id of a shared table (below) and asserts that they carry the same path segment. The same table is read by the live-test client's own tests, so the two suites cannot drift. A title with a lone surrogate is refused with a message, because `encodeURIComponent` throws on it.

**Rule 2: ids the blob path cannot carry are refused before any request, in Fusion mode.** `isStorableBlobId(id)` is false for: a non-string or empty id; an id with a lone surrogate; an id containing `%`, `;`, `\`, or a control character (below U+0020 or U+007F); and an id with an empty segment or a segment equal to `.` or `..` when split on `/` (this includes a leading or trailing `/` and `//`). Save refuses such a title with a message that names the reason. Delete refuses to send the request. Load answers "cannot be opened". Why each: `%`, `;`, `\`, NUL, `//` and dot segments are refused by the gateway (facts above; `%` was shown live, the rest from source); the browser rewrites `.` and `..` before the gateway sees them. The predicate is stricter than the gateway in three places, all deliberate: a trailing `/` and an empty segment (the gateway accepts them, but the blob store's treatment of them was never probed), control characters other than NUL (no title typed into the Save box contains one), and lone surrogates (they cannot be encoded). It is a no-op for every plain title.

**Rule 3: the save captures, looks up, asks, looks again and then writes.** The service function keeps its signature and gains an optional fourth argument: a function that receives the existing dashboard's title and owner (as one object, `{ title, owner, byYou }`, where `byYou` is the rule-5 test below) and returns whether to replace it. With none supplied, an overwrite is refused (fail closed). The dashLoader controller supplies a function that uses `window.confirm`. The deprecated dashboard-control panel passes none, so it can save new titles and cannot overwrite; it has no template in the build, so no user can reach it.

1. **Capture, synchronously, when the user clicks Save.** The mode (`fusion = config.USE_FUSION`, read once), a deep copy of the dashboard being saved (`angular.copy`, so that later edits to the page's dashboard cannot reach the write), the title, the server (`config.banana_server || current.solr.server || config.solr`, plus the index), the Fusion blob URL, the lookup URL, and the current address (`$location.url()`). Nothing later in the save reads `config.USE_FUSION`, `dashboard.current`, or the shared client's server again: the route can change `dashboard.current` while the save waits, and a settings toggle can change the mode.
2. **Validate the title** (Fusion: rule 2). An empty or undefined id is refused in both modes.
3. **Fusion mode only: wait for the session user.** The session promise is created on the first Fusion save if the page started in Solr mode and none exists. The wait has a timeout of three seconds, after which the owner is the fallback `guest` (as in 1.6.30, where a late lookup also meant `guest`). A page in Solr mode has no session to wait for.
4. **Look up the stored dashboard with `$http`, using the captured URL, never through the shared client.** Each look-up carries a timeout (`timeout` in the request configuration of AngularJS 1.0.8, ten seconds), and a request that times out is read as "could not check". Fusion: `GET <blob url>` with the header `Cache-Control: no-cache`. Solr: `GET <server><index>/select?wt=json&rows=1&fl=id,<user field>,<dashboard field>,_version_&q=id:"<escaped id>"&_=<timestamp>` (rule 6; the Solr request uses a cache-busting parameter and not a header, because a non-standard request header makes a cross-origin Solr answer a preflight that it refuses). Decide:

| Lookup answer | Result |
|---|---|
| Fusion 404 whose body is the blob store's own not-found error (`error` is `BLOB-0001`); Solr 200 with no document | No dashboard under that title: go to step 6. |
| Fusion 200 whose body is a one-element array with a `banana_dashboard_s` string; Solr 200 with a document | A dashboard exists: go to step 5. |
| Fusion 200 with any other body, or 204 (a folder) | Something that is not a Banana dashboard is stored under that name: refuse; never overwrite it. |
| Any other answer: a 404 with another body, 401 (the promise resolves with no value while the browser goes to the login page), 403, 5xx, no answer, an unparsable body, or a resolved `undefined` | Banana cannot tell whether the title is taken: refuse. A resolved `undefined` is "stop", never "no document". The user sees "could not check whether this title exists" and nothing is written. |

5. **Ask.** `window.confirm` with plain text (it is not HTML, so the id and the owner are not HTML-escaped there): `A dashboard named "<title>" already exists. It was saved by <owner>. Saving replaces it, and the earlier version cannot be restored. Replace it?` The owner is the first line of the stored owner text, or "an unknown user" when absent. The words "by you" replace the name only when the stored owner equals the session user and that session user is a real one, never the fallback `guest` (every dashboard saved by 1.6.30 under a missing session would otherwise claim to be the user's). A decline, or a dialog that cannot be shown (which makes `confirm` answer false), stores nothing. After a yes, repeat the lookup of step 4. The recheck compares everything the user was shown against what is stored now: Fusion, the whole response text (owner, title and dashboard JSON); Solr, `_version_` (rounded the same way in both reads, so equal for an unchanged document) and, as well, the dashboard text and the owner. A difference, or a stored object that is no longer a Banana dashboard, stops the save with "changed while you were deciding" and writes nothing. If the dashboard is now gone, continue. Every recheck failure follows the table above.
6. **Write, in the same synchronous turn that sets the client.** Immediately before the call, and with no asynchronous step in between, set `sjs.client.useFusion(fusion)` and `sjs.client.server(<captured server or blob API>)` and call `doIndex`: Fusion `PUT <blob url>?resourceType=banana`, Solr `POST <server><index>/update?commit=true`, body unchanged. The saved dashboard is the copy captured in step 1. After a successful write, the address is set to the saved dashboard two seconds later only if it is still the address captured in step 1; a user who has gone to another dashboard in the meantime is not moved.

**The outcome contract.** The service's promise resolves only after the write succeeded. Every outcome that writes nothing rejects with a reason: invalid title, not a dashboard, could not check, declined, changed while deciding. A failed write rejects as it does today. The dashLoader controller therefore never shows "Dashboard Saved" for a refusal; it maps each reason to its own message (a decline is shown as "Not saved: the existing dashboard was left as it was", not as an error) and does not clear the title box or redirect.

**Rule 4: the owner is the session user where there is one.** `getFusionUsername` returns `user.username` when the session has one and `guest` otherwise: for a session with no user name (an API key), for a failed lookup, and for a body with no `user`. The dashboard service keeps the user it resolved, and a save sets both the stored owner field and the `username` in the saved dashboard JSON from it, never from the loaded JSON. In Solr mode there is no session, and the owner stays what 1.6.30 wrote (the value in the dashboard JSON, `guest` by default). The owner is a label for the person confirming an overwrite. It is not an authorisation check: any user with the blob roles can write any dashboard, and behind a shared-account proxy the label is the shared account.

**Rule 5: Solr delete is a delete-by-id sent as JSON.** `POST <server><index>/update?wt=json&commit=true`, `Content-type: application/json`, body `{"delete":{"id":"<id>"}}`, built with `JSON.stringify`. The id is a string literal in the JSON, never part of a query, so a title such as `*` or `x" OR title:"*` deletes at most the document whose id is exactly that text. This replaces both the 1.6.30 `stream.body` GET and the delete-by-query POST on the development line. For every id Banana saved the request deletes the same single document the old request meant to delete; on Solr 7 and later it works where the 1.6.30 request did not. The mode, the server and the id are captured when the user clicks Delete, and the client's server and mode are set in the same synchronous turn as `doDelete` (today there is no asynchronous step in the delete; the rule keeps it that way, and a test pins it).

**Rule 6: the Solr load and existence queries are escaped and encoded.** The id goes into a quoted phrase with `\` and `"` escaped by a backslash, and the whole `q` value is passed through `encodeURIComponent`. Load keeps matching on the title field (1.6.30 behaviour); the existence check matches on `id`. A plain title produces the same query as before after the server decodes it. The existence request is built from the captured server and sent with `$http`, so a re-pointed shared client can neither redirect it nor make it answer for a data collection.

**Rule 7: the load path reports what happened.** The response transformer never throws: it returns the dashboard when the body is one and otherwise leaves the data alone. The decision is made from the response: a 2xx whose body holds no dashboard (Fusion `response[0]` missing, a 204, Solr with no document) is "could not find dashboard named …"; status 0 is "could not contact"; any other status is "could not find". The id is escaped in the message (as the existing code does). This covers the `docs[0]` failure and the error alerts that the recorded-response specs mark as known defects.

**Rule 8: links, the route and the list carry the id intact.** (a) Every link Banana builds for a saved dashboard (the list entry, the address set after a save) puts `encodeURIComponent(encodeURIComponent(id))` after `/dashboard/solr/`. AngularJS 1.0.8 decodes once, so the route receives the singly encoded id, which contains no `/`. (b) For the route types that load a stored dashboard (`solr`, `elasticsearch`, `temp`), and for no other type, the route decodes the id once more with `decodeURIComponent` and, if that throws, uses the text as it is. The `file` route is never decoded a second time, so `#/dashboard/file/..%252F..%252Fx` cannot reach `app/dashboards/../../x`. A plain id, and a link written by 1.6.30 for an id without `%`, resolve exactly as before. In Fusion mode the extra decode changes nothing only because a stored id cannot contain `%`. (c) A listed Fusion id loses its first character only when that character is `/`. (d) The list is sorted by `id`, the field blob entries have, and the sort stays in the browser: the list request keeps exactly the `q` and `resourceType` parameters, since a sort parameter on it would also be refused by the live-test client's list rule. (e) The id in every alert that Banana sets for save and delete is HTML-escaped exactly once: where the alert text is still rendered as HTML, the code escapes the id; where another change has already escaped it, this change adds no second escape and does not remove the first. The text shown by `window.confirm` is plain text and is never HTML-escaped.

**Rule 9: delete sends the request only for an id that passes the checks, and reports the outcome.** The id comes from a row of the listing (never from typed text). It passes rule 2 in Fusion mode. A rejected request leaves the row in the list and shows "Dashboard Not Deleted" (a 404 is shown the same way). The row is removed only after a real success: a resolved `undefined` (a 401) is a failure, so the row stays. The delete promise rejects in every case that did not delete, so the controller's Fusion shortcut (which treats every resolution as success) cannot report one.

**Rule 10: the delete URL form is fixed.** In Fusion mode a dashboard is deleted with exactly

`DELETE <SYSTEM_BANANA_BLOB_API>/<encodeURIComponent(id)>`

with no query string, no fragment, no further path segment, no body and no custom header. The live-test client's rule (`test/live/fusion-client/rules.js`, function `deleteUrl` at `:28-30` and `classifyDelete` at `:297-315`, described in ADR 8) already requires exactly this form: `origin + '/api/blobs/' + encodeURIComponent(id)`, no query, for an owned id. No change to that rule or to its tests is needed. The existence GET matches the rule's read row (no query allowed, `rules.js:168-170`), and the PUT matches `classifyPut` (`:280`); the `Cache-Control` header on a GET is not checked by that rule. If a later change adds a query (for example `?commit=true`), the rule, its tests and ADR 8 must change in the same change; the shared id table (rule 1) fails first. Odd-id deletes (`/`, `?`, `#`, space) follow from the PUT and GET results and were never run live. The live runs delete only plain `banana-it-<run>-<n>` ids.

| The id of a save with a `ttl` | The temporary-dashboard save, which has no caller in the UI and no id | The blob id would be `undefined` | Unreachable; rule 3 step 2 refuses an undefined id | Remove the dead code later | Yes |

## Consequences

**Better.** A dashboard can no longer be replaced by accident or by a second user without a message that names its owner. A crafted title cannot delete other dashboards, in either mode. Delete, load and save name the same stored object for every title the blob path can carry. Titles that cannot be stored are refused with a reason instead of failing at the gateway or addressing another id. Alerts cannot carry markup from a title. A save cannot be redirected to a data collection by a panel refresh.

**Costs and behaviour changes against 1.6.30.**

- Saving under an existing title now asks first, every time, including a user's own dashboard, with no setting to turn it off. This is the one deliberate change of an existing behaviour. It is justified by the data loss it prevents and was decided by the project owner.
- A save needs one extra request (the lookup), two when the user confirms an overwrite. A save also fails closed when the lookup fails.
- In Fusion mode, the first save of a new title makes the browser log a 404 in its console: that is the lookup asking for a dashboard that does not exist yet, and it is the expected answer, not an error.
- Fusion titles containing `%`, `;`, `\`, a control character, a lone surrogate, a trailing `/`, an empty segment, or a `.` or `..` segment are refused at save. The gateway already refuses most of them, so nothing that worked stops working; the exceptions are named in rule 2.
- Solr delete sends a different request (POST JSON delete-by-id). It works on Solr 7 and later, where the 1.6.30 request did not.
- The owner recorded by a save is the session user, where the 1.6.30 value was `guest` or the previous saver.
- The list is sorted by id and shows ids with `/` correctly.

**First run after deployment.** No data migrates. The first overwrite of any title asks.

**Release note text.** "Saving a dashboard under a title that already exists now asks for confirmation and shows who saved the existing one. Deleting a dashboard in Solr mode deletes exactly that dashboard. Dashboards whose titles contain `?`, `#` or spaces can be opened and deleted in Fusion mode, and titles with `/` work in this version. Titles containing `%`, `;` or `\` cannot be stored in Fusion and are refused when saving. The saved owner is the logged-in user. Version 1.6.30, which Fusion itself still serves, mishandles titles containing `/` in its saved-dashboard list (it opens and deletes a different id), so avoid `/` in titles while that version is in use."

## Decisions for the maintainers

Decided on 2026-11-07 by the project owner: the overwrite confirmation replaces the silent overwrite by default, always on, with no setting (rejected options 4 to 6).

Accepted on 2026-11-07 by the project owner, with the residuals below and the two deviations from the earlier acceptance text:

1. **Solr delete as JSON delete-by-id instead of an XML delete-by-id with escaping.** This is a deviation from the earlier wording of the acceptance text, which says "XML-escaped". The aim (a crafted title deletes at most its own document) is met either way. JSON is recommended (option 7). The XML form with escaping is the fallback. Accepted: the delete is a JSON delete-by-id.
2. **Titles containing `%` cannot round-trip in Fusion mode.** The acceptance text asks that titles with `/`, `?`, `#` or `%` round-trip. The gateway refuses a decoded `%` in the path (`gw:...StrictFirewallFilter.java:102-108`, seen live as a 400), so a title with `%` can be neither stored nor loaded nor deleted, and this design refuses it with a clear message. The text should be amended, or the deviation logged. Accepted: a title containing `%` is refused in Fusion mode, with a message that says why.
3. **The residuals above**, especially the race, the missing undo, and the mis-targeting of `/` titles by 1.6.30. Accepted, so the implementation could start; the conditional-write probe is the follow-up that could remove the race.

## Verification plan

**Unit tests, each failing on the current code and passing after the change** (run in the real browser the unit suite uses, with AngularJS 1.0.8):

1. Overwrite: a lookup that finds a dashboard shows the stored owner; declining writes nothing and rejects; accepting writes once; every non-"free" lookup answer writes nothing (a 404 with another body, 401 resolving with no value, 403, 5xx, no answer, a resolved `undefined`); a non-dashboard body or a 204 writes nothing; no confirm function refuses. Both modes.
2. **Recheck, Fusion:** a change of the dashboard content with the same owner between the lookup and the recheck writes nothing. **Recheck, Solr:** a same-owner change (`guest` in both reads, different `_version_` and dashboard text) writes nothing. A cached lookup (a stub that returns the first answer) is defeated by the header (Fusion) or the changing parameter (Solr).
3. **The shared client is re-pointed:** during the lookup, and again during the recheck, the test re-points `sjs.client.server` and recreates the client with `sjsResource()`, then asserts that the write URL is the captured saved-dashboards URL (Solr `…/<index>/update?commit=true`; Fusion the blob URL) and that no request went to the data collection. The same test for delete. A second test flips `config.USE_FUSION` during the confirm and asserts that the recheck and the write use the mode captured at the click.
4. **The outcome contract:** for each of declined, changed, not a dashboard, could not check, and invalid title the promise rejects with its reason and the controller does not show "Dashboard Saved", does not clear the title and does not redirect.
5. **The session wait:** a session promise that never answers falls back to `guest` after the timeout and the save continues; a page that started in Solr mode and is toggled to Fusion creates the promise at the first Fusion save.
6. Solr delete: the body is exactly the JSON of the id, for ids with `& < > " ' \`, `*` and `x" OR title:"*`; the URL parameters and content type are as stated. Solr load and existence queries: the escaped, encoded `q` for the same ids; the existence query asks for `id`, the user field, the dashboard field and `_version_`.
7. Fusion codec: one shared table of ids (plain, `/`, `?`, `#`, space, `&`, `"`, `<`, `>`, `'`, `+`, non-ASCII) and their `encodeURIComponent` forms is read by the unit suite and by the live-client suite; for each id the existence GET, the load GET, the save PUT and the delete DELETE share the path segment, and the delete URL equals the live client's `deleteUrl` result. A source-level test fails if a Fusion blob URL is built without the codec.
8. Rule 2: every refused class (`%`, `;`, `\`, control, a lone surrogate, `.`, `..`, `//`, leading and trailing `/`, empty) sends no request; plain ids pass. A real-browser check shows that a request for `..` is rewritten by the browser (the reason for the rule).
9. Owner: a session with a user name gives that name; a session without one (derived from the recorded login by removing the field) and a failed lookup give `guest`; the saved JSON and the stored field agree. The dialog says "by you" only for a real session user who equals the stored owner, never for the fallback `guest`; it shows only the first line of the stored owner text; its text is not HTML-escaped.
10. Load: the transformer does not throw on a 404 body, a 204, an empty body, a Solr result with no document, or status 0; each shows the stated alert. The pending specs for these cases are switched on, and are first run with the logging exception mode to see which defect occurs in production. A Fusion 404 whose body is not the blob-not-found error is not read as "free" by the save.
11. Route and links: with the real AngularJS location code, a link for `a/b`, `q?x#y` and a plain id round-trips to the same id; a link written by 1.6.30 for a plain id and for an id with a space resolves as before; a malformed `%` falls back to the text; the `file` route is not decoded a second time (`..%252F..%252Fx` stays `..%2F..%2Fx`).
12. List: an id with `/` keeps its first character; entries sort by id in the browser; the list request carries only `q` and `resourceType`.
13. Alerts: an id containing markup is escaped exactly once in the saved, deleted and not-found messages, whichever of the two changes to the alert code is applied first.
14. Delete: a resolved `undefined` (401) leaves the row in the list and shows "Dashboard Not Deleted".

**Live, on Fusion 5.9.16 with plain `banana-it-<run>-<n>` titles only, through the live-test client and its browser interceptor:** first save through Banana's own UI (no confirmation, the lookup answers 404 with the blob-not-found body); a second save of the same id with the dialog accepted (the document is replaced; the stored owner is the session user, not `guest`); a second save with the dialog declined (nothing written); a delete through the list, with the interceptor confirming the URL equals `<blob api>/<id>` and the read-back answers 404; the stored owner equals the logged-in user; the response's cache header is recorded. Odd titles are not run live and are covered by the unit tests and by the earlier probe results recorded above. Banana's own lookup GETs are reads, and the interceptor allows them.

**Cannot be proven here:** Solr-mode behaviour against a live Solr; DELETE of ids with reserved characters; saving `a/b` when `a` exists, and the folder cases (a probe on owned ids); the conditional-write question (a probe needs a reviewed, small extension of the live client so that it may send a header on a PUT of an owned id); non-admin permissions (a second, non-admin user); the production error path of load, until the pending specs run with the logging exception mode; browser handling of the double-encoded link in browsers other than the one the unit suite runs; the blob service's own cache header.
