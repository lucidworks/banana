# 0003. Standalone hosting: a same-origin proxy in front of Fusion, per-user login only

Date: 2026-11-05
Status: Accepted. Implemented by [ADR 0023](0023-docker-image.md). Superseded in part by [ADR 0029](0029-content-security-policy-without-unsafe-eval.md): the image's baseline script policy no longer carries `'unsafe-inline'` or `'unsafe-eval'` (see the notes beside the policy table and in the consequences).
Accepted: 2026-11-06

## Context

### Problem

Banana is designed to be served by Fusion itself, at `/admin/banana/`. Run anywhere else, for example as a container next to Fusion, it stops working in three ways.

1. **It cannot authenticate.** The browser app never sets `withCredentials` and never sends an `Authorization` or API-key header (`src/app/app.js:88-90`). It relies on the Fusion session cookie being on the page's own origin. It looks the session up at the page's own host (`src/app/services/lucidworksSrv.js:14-15`). A page on another origin has no cookie and no way to get one.
2. **Its login redirect is wrong.** On a 401 the app navigates to `../login?return=...`, relative to its own page (`src/app/app.js:97-110`). Under `/admin/banana/` that resolves to `/admin/login`, which Fusion serves. At `/` or `/banana/` it resolves to a path on the Banana host that does not exist.
3. **Nothing hardens it.** The repository ships no web server configuration and no security headers (`src/WEB-INF/web.xml:1-18`), so a standalone Banana can be framed and has no content policy.

Fusion 5.9 offers no safe way around the first problem from another origin. Its gateway answers 403 to any request that carries a foreign `Origin` header unless allowed origins are configured on Fusion. Its session cookie is host-only and `SameSite=Lax`. Everything Banana does (query, list collections, load, save and delete dashboards) goes through `/api/`.

The consequence of getting this wrong is not subtle. A deployment that works around the problems above by putting a Fusion credential into the proxy gives every person who can reach Banana that one Fusion identity, including write and delete access to the blob store where saved dashboards live, and, as the analysis below shows, a copy of that identity's session cookie. This decision therefore ships exactly one identity model: every person logs in to Fusion as themselves.

This ADR fixes the design for running Banana outside Fusion, in a container, against Fusion 5.9.16. It is design only. No Dockerfile, proxy configuration or source change is part of it.

> Update, 2026-11-07: the design is implemented, and the container is described in [ADR 0023](0023-docker-image.md). The two application settings that this record proposes (their names are marked "proposed" below) exist with exactly these names and defaults: `FUSION_LOGIN_URL` (default `../login`) and `FUSION_SESSION_API` (default `/api/session`). Several files cited below no longer exist: the servlet descriptor `src/WEB-INF/web.xml` and the Maven and Ant files were removed ([ADR 0026](0026-remove-war-build.md)), and `Gruntfile.js` and `src/app/components/require.config.js` were replaced by the webpack build ([ADR 0009](0009-webpack-build.md)). Their line numbers, like every plain `path:line` here, are those of the base commit named below.

### Behaviour of the last release

Release 1.6.30 is what Fusion 5.9.16 serves at `/admin/banana/`. It has no standalone mode at all. Where it differs from a standalone container:

- Banana and the session cookie share the origin of the Fusion admin UI, so `../login` reaches Fusion's login (`rel:src/app/app.js:97-110`) and the session lookup works (`rel:src/app/services/lucidworksSrv.js:14-15`).
- Fusion adds `X-Frame-Options: SAMEORIGIN` to the pages it serves (live), and no content policy.
- The default configuration uses the Fusion paths under `/api/` (`rel:src/config.js:66-80`).
- It shares the template-evaluation weakness, the swallowed errors, the overwrite-without-check save, the 15 s query limit and the `solr.server` field in every saved dashboard (`rel:src/app/services/dashboard.js:293-296`, `rel:src/app/app.js:88-119`).
- A stored `{{...}}` runs in the Fusion admin origin there, which is a larger prize than in the container's origin. The container's origin does expose the admin UI by default (D2), so the difference is the container's content policy and an off switch for the admin route, not a different set of reachable routes.

Every residual below says whether 1.6.30 shares it. Inside Fusion nothing in this ADR changes: every new setting defaults to the 1.6.30 value (`../login`, the same-host session path, the existing `config.js`).

## Options considered

1. **Cross-origin: Banana on its own origin calling Fusion directly.** Rejected. It needs code Banana does not have (credentialed requests), a Fusion gateway change (allowed origins, methods, headers), and a cookie that the browser will not send, because the session cookie is host-only and `SameSite=Lax`. Every saved dashboard would need its relative `solr.server` rewritten. The swallowed-error interceptor would hide every CORS failure. Recorded as a non-goal in its own decision (ADR 0005).
2. **Same-origin proxy that forwards `Origin` unchanged and relies on Fusion's allowed-origins list.** Rejected as the default. It requires the operator to change gateway configuration, and POST search and PUT save need methods and headers set too. It stays possible for an operator who prefers it, but it is not part of the tested design.
3. **Same-origin proxy that injects one Fusion credential for everyone (API key or HTTP Basic).** Rejected, and not implemented. Every visitor becomes one identity with that identity's blob write and delete permission, any stored script runs with it, the gateway hands that identity's session cookie to every visitor, and a cross-site page can reach it. See "Not provided by this image".
4. **Banana implements its own login form and handles passwords.** Rejected. Banana would then handle credentials and have to know every realm. Fusion's login page already does this.
5. **Serve Banana only at `/admin/banana/` inside the container.** Rejected as the single layout. It couples the container's URL space to Fusion's. It is kept as an optional second mount (D1) because it is the one layout where today's code works unchanged.
6. **Bake `config.js` into the image at build time.** Rejected. One image per environment. `config.js` is already excluded from bundling for exactly this reason.
7. **Ship a Content-Security-Policy without `unsafe-eval`.** Rejected for now. AngularJS 1.0.8 compiles expressions with `Function`, and the template engine does too, so such a policy would break the app. It is tightened only when the code stops needing it.
8. **Proxy only the three or four API prefixes Banana uses, always.** Rejected. It would break dashboards that name other routes, such as `/api/solr/`, and it protects nothing that Fusion's own authentication does not already protect, provided the container is deployed where its audience may already reach Fusion's API (the declared audience precondition under D2). The container holds no credential, so a narrower route list would only hide endpoints that Fusion itself serves to anyone who can reach it.
9. **Trusted-HTTP realm as an implemented identity mode.** Rejected, and not implemented. It needs a Fusion realm created by an administrator and a separate authenticating front end, and Fusion's trust rule (peer address or any value of a forwarded header) cannot tell the front end from anyone else who reaches the container. See "Not provided by this image".

## Decision

The supported standalone mode is a container that serves Banana's static files and acts as a same-origin reverse proxy to one Fusion instance. The browser only ever talks to the container's origin. **Each person logs in with their own Fusion account**, on Fusion's own login page, through the proxy. The container holds no Fusion credential of any kind, injects nothing, and never writes a session cookie of its own.

The shared-credential identity mode that was considered earlier does not apply: nothing in the image holds a credential, so there is no shared account whose session cookie could be handed out, no cached Basic credential for a cross-site page to reuse, and no mode to switch between. The one hazard that remains from the mode question (browsers that still hold a shared account's cookie from some other deployment) is recorded under "Not provided by this image".

**D1. Path layout.**
- Banana is served at `/`. Every asset URL in the app is relative (`src/app/components/require.config.js:7-9`), so no prefix setting is needed.
- `/healthz` answers 200 from the container itself and never touches Fusion.
- Optionally, the same files are also served at `/admin/banana/` when `BANANA_ADMIN_MOUNT=on` (default off). This is the layout Fusion itself uses, so the `../login` default resolves there as it does in Fusion. It is how the "inside Fusion" layout is exercised behind the proxy (ADR 0004). Because the mount reproduces Fusion's layout, the container refuses to start with the mount on and the admin route off (D2).
- The mount serves the same static files but its own `config.js`. The page at `/admin/banana/` asks for `/admin/banana/config.js` (`src/app/components/require.config.js:4-9`). That path is answered by an exact-match location that returns a second rendered file in which the login URL and session path are left at the 1.6.30 defaults (`../login`, same-host session path), so the mount behaves as Fusion's own copy does. The root page at `/` gets the file that sets the login URL (D6).
- When the mount is off, `/admin/banana/` returns 404 from the container, and so does the admin UI's own "Dashboards" menu entry (`fw:app/common/services/menu-service.js:192`) for anyone who reaches the admin UI through the container. That is documented behaviour, not a defect; such users open Banana at `/`.
- Banana is not served at `/banana/`. A third location adds a layout nobody needs.

Matching rules:
- Matching is done on the normalized path: percent-decoded once, dot-segments resolved, repeated slashes merged, query string excluded. Banana's own requests (`/api/collections`, `/api/blobs?resourceType=banana`, `/api/blobs/<id>`) all fall under the `/api/` prefix. There is no per-endpoint rule, so a rule cannot miss a call that lacks a trailing slash.
- The request is forwarded to Fusion with the original request URI, unchanged. The container never rewrites a path. Banana's dashboard titles are blob ids and may contain encoded characters, which must reach Fusion as sent (Live: Fusion decodes `%3F`, `%23`, `%20` and `%2F` once and rejects `%25`).
- The boundary that matters is where the container serves local files (`/admin/banana/`, `/config.js`, `/healthz`), not authorization: Fusion authorizes every proxied request by the user's own session, so a path-normalization difference between the container and Fusion cannot grant a user anything they could not already do by calling Fusion directly. The tests check that dot-segment, encoded and doubled-slash forms of `/admin/banana/`, `/config.js` and `/healthz` end up at the container's own handlers and never at Fusion.
- A request whose raw path holds a backslash, a NUL or another control character is refused with 400.
- An unmatched path is 404 from the container.

**Declared precondition: the container's audience.** The container holds no credential and adds no privilege, so what a person can do through it is what Fusion lets an unauthenticated or logged-in caller do. That is true only for a person who could already reach Fusion's API. Fusion itself serves a number of endpoints with no session: `/api/session` (password login), `/api/internal`, `/api/saml`, `GET /api/saml/*`, `/api/oauth/*`, `/auth/**`, `/admin/login`, the admin UI's scripts, styles, images and fonts, and `GET /api` with the Fusion version, the enabled realm names and types and the service status (`gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewaySecurityConfig.java:61-95`, `gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewaySecurityConfig.java:163-164`, `gw:src/main/java/com/lucidworks/cloud/gateway/security/api/ApiController.java:216-229`). The container proxies the whole `/api/` prefix, `/auth/` and (unless switched off) `/admin/`, so all of these become reachable by everyone who can reach the container. The container does not proxy the open `POST /api` (D2) or `/api-ws`, `/oauth2/` and `/actuator/`.
- Trigger: the container is reachable by people who cannot reach Fusion, for example Fusion on a private network and the container on a wider one.
- Effect: the whole proxied surface is exposed to that wider audience, including the endpoints above and password login against Fusion's realms, which an attacker can try without any other foothold.
- Bound: Fusion's own authentication and authorization. The container holds no credential, so nothing beyond what Fusion allows an unauthenticated caller is open.
- Remedy: deploy the container only where everyone who can reach it may already reach Fusion's API, or put a network or authentication gate in front of the container. `FUSION_PROXY_ADMIN_UI=off` narrows the surface to the API and the login page but does not remove the open endpoints under `/api/`.

Exposing `/auth/` and `/admin/` through the container also means two things. First, under the precondition above, anyone who can reach the container can load the Fusion admin UI's static assets and login page, and the admin UI itself for anyone who logs in with an administrative role. Second, the container is only a supported host for Banana. The admin UI behind it is best effort, with no websocket route and no support promise, and its own writes (`/api/ui-logs`) travel through the container. Operators who want a narrower surface turn the admin route off; the start-up check in D6 refuses a login URL under `/admin/` while it is off.

SAML, OIDC and Kerberos logins start flows on Fusion's own host and come back to it, so they very likely set the session cookie on Fusion's origin, not the container's. They are out of scope: only username-and-password realms (as the login page posts them) are supported through the proxy. The effect of trying an SSO realm is a visible login loop, with no change to anyone's privilege and nothing stored. Users who need an SSO realm use Fusion's own address.

**D3. Host and Origin handling (validate, then rewrite).**
The public address is required: `BANANA_PUBLIC_ORIGIN` (scheme, host and optional port; no path) must be set or the container refuses to start. `BANANA_ALLOWED_ORIGINS` optionally lists further origins that are accepted as the container's own (for example a second public name). `BANANA_REDIRECT_HOSTS` optionally lists host names that are known aliases.

The gateway rejects a foreign `Origin` (see table), so the proxy sets `Origin` to the Fusion origin and `Host` to the Fusion host on every proxied request. That rewrite also switches off Fusion's cross-site check for everything behind the proxy, so the proxy performs the checks itself, before rewriting:
- Comparison rule for `Host` and `Origin`: both sides are compared after lower-casing the scheme and host and dropping the default port (`:443` for https, `:80` for http), so an origin written with an explicit default port and in mixed case is the same origin as the plain lower-case form. A non-default port is significant. The configured values are normalized the same way at start. A `Host` header carries no scheme, so the default port that is dropped is the one of the scheme of the origin it is compared with: the public origin's scheme for the public host and for every `BANANA_REDIRECT_HOSTS` entry, and each entry's own scheme for `BANANA_ALLOWED_ORIGINS`. Redirect-host matching includes the port: an entry is a host or `host:port`, and an entry without a port matches only the default port, never any port. Without this an `Origin` that spells out the default port would not match the configured value and every search POST and every save would get 403.
- `Host` check (applies to every request except `/healthz`; `/healthz/upstream` is not exempt, so a monitor sends the public name as `Host`): the request's `Host` must be the public host of `BANANA_PUBLIC_ORIGIN` or of an entry in `BANANA_ALLOWED_ORIGINS`. A `Host` listed in `BANANA_REDIRECT_HOSTS` gets a 308 redirect for GET and HEAD to the same path on the public origin; the `Location` is built from the configured origin, never from the request. Any other method to a redirect host (POST, PUT, DELETE and the rest) gets 421 with the same static page and is never forwarded, because a browser would replay neither the body nor the intent safely and a 308 on a write could hide a lost save. Any other `Host` gets 421 and a short static page that names the public address. A redirect host must be a name users type, never the name a Host-rewriting front end sends to the container: if it were, a GET would get a 308 to the public origin, the front end would rewrite `Host` again and the browser would stop with "too many redirects". The loop is visible, only GET and HEAD are involved and nothing is stored.
- A front end in front of the container must preserve the client's `Host` (for example `proxy_set_header Host $host` in nginx, not the default `$proxy_host`), or list the name it sends as an allowed origin (not as a redirect host). A front end that rewrites `Host` to an internal name such as `banana:8080` gets 421 on every request except `/healthz`. The failure is visible and stores nothing, and it is documented in the deployment notes and tested. Fusion is not contacted. This closes DNS rebinding against a plain-HTTP internal listener (an attacker-controlled name that resolves to the container carries its own `Host`), and it turns the alternate-hostname failure (a user on a second name whose writes would otherwise be refused and swallowed) into a visible redirect or a visible page.
- `Origin` check: no `Origin` header is allowed; `Origin` equal to the public origin or an allowed origin is allowed; anything else, including the literal `null` (which the gateway would let through, `gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewayConfiguration.java:169-171`), gets 403 from the proxy. Fusion is not contacted.
- `Sec-Fetch-Site` check on `/api/`: a request whose path is under the `/api/` prefix and whose `Sec-Fetch-Site` is `cross-site` or `same-site` gets 403 from the proxy, for every method, and Fusion is not contacted. `same-origin`, `none` (typed address, bookmark) and an absent header are allowed. The rule covers every method under `/api/` and nothing else, apart from the single refusal named at the end of this item: the exact `/api` route, `/auth/`, `/admin/`, `/config.js`, the static files and `/healthz` are not subject to it for GET and HEAD, so navigating to the container, loading Fusion's login page and following the login redirect are unaffected. Banana's own calls are same-origin XHR to the container's own host, so they carry `same-origin` and pass; the proxied login form posts to `/api/session` from a page on the container's own origin and passes too. Outside `/api/` (everywhere except `/healthz`), a request with `Sec-Fetch-Site: cross-site` and a method other than GET or HEAD is also refused with 403 and never forwarded; `same-site` is not refused there, and GET and HEAD are never refused there.
  - Top-level navigation to an `/api/` URL: following a link from another site sends `cross-site` (a sibling sub-domain sends `same-site`) and gets 403 instead of the Lax-cookie GET that Fusion would serve. A person who types or bookmarks an `/api/` URL sends `none` and gets the response, and so does a link opened from a desktop mail or chat application, which also sends `none`. The effect for a person who clicks an API link in a web mail client is a 403 page; that is intended. A redirect chain keeps the initiating site's value, so a cross-site page cannot launder a request through a redirect to the container.
  - A browser that does not send `Sec-Fetch-Site` is allowed through, because the container cannot tell it from a non-browser client. For those browsers the cross-site GET exposure described under D10 remains as it is in Fusion and 1.6.30 (it is a recorded residual). The header cannot be set by page script, so a browser that does send it cannot be made to lie.
- Responses from Fusion that redirect to the Fusion origin are rewritten to relative redirects. No response body is rewritten.

**D4. Identity and forwarding headers.**
The container presents Fusion with nothing a client could use to impersonate someone. It adds no identity or address header of its own.
- The container DELETES `X-Forwarded-For`, `X-Real-IP` and `Forwarded` from every request, and does not write replacements. The container sends no client address, and the TCP peer the gateway sees is the container. A component between the container and the gateway, such as the ingress in front of a Kubernetes service, can add its own `X-Forwarded-For` (carrying the container's address, never the client's) and can overwrite `X-Forwarded-Proto`; the container neither controls nor relies on that, and the safety argument below does not depend on it, because it rests on the identity header being removed, not on any address. The earlier idea of writing the peer address into those headers is dropped: it would put a value in a header that a Trusted-HTTP realm may be configured to trust (`gw:src/main/java/com/lucidworks/cloud/gateway/security/realm/trustedhttp/CompiledTrustedRealm.java:57-61`). It also deletes `X-Forwarded-Host`, `X-Forwarded-Port` and `X-Forwarded-Prefix`. It sets `X-Forwarded-Proto` from the scheme of `FUSION_URL`, the hop it actually makes, so the scheme agrees with the `Host` and `Origin` it sets for that hop; the gateway marks the session cookie `Secure` from the request scheme or this header (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:96-100`). With an https Fusion URL, which is the supported setup, this is `https`. An `http://` `FUSION_URL` is refused at start (D5), so the header is never `http` outside development. With a plain-http public origin (development) the browser-side `Secure` flag is handled by `BANANA_INSECURE_COOKIES` (D5), not by this header.
- The container strips a list of identity and group headers from every request before it reaches Fusion. The built-in list is `X-Remote-User`, `X-Forwarded-User`, `Remote-User`, `X-Remote-Groups`, `X-Forwarded-Groups`, `X-Auth-Request-User`, `X-Auth-Request-Email` and `X-Auth-Request-Groups`. `BANANA_STRIP_HEADERS` (comma-separated names, matched case-insensitively) ADDS names to that list; it never replaces it, and an empty or blank value changes nothing, so stripping cannot be switched off. A name that is not a valid header name stops the container at start. A start-up log line prints the effective list.
- **Declared precondition: for every enabled Trusted-HTTP realm on that Fusion, its identity header name and its groups header name are in the strip list.** The gateway's trust test passes when the peer address matches an allowed address, or when any value of any configured trusted-proxy header matches, and a visitor can supply any header the container does not delete (`gw:src/main/java/com/lucidworks/cloud/gateway/security/realm/trustedhttp/CompiledTrustedRealm.java:57-61`). So the precondition cannot be stated in terms of addresses. What stops the attack, whatever the realm trusts, is that a token is created only when the identity header is present (`gw:src/main/java/com/lucidworks/cloud/gateway/security/realm/trustedhttp/CompiledTrustedRealm.java:67-75`), and the container removes that header from every client request. The converter reaches the Trusted-HTTP step only when no earlier credential was found (`gw:src/main/java/com/lucidworks/cloud/gateway/security/AuthenticationTokenConverter.java:72-79`). Header names in a realm are free-form, so the operator, who owns the realm, adds its identity and groups names to `BANANA_STRIP_HEADERS`.
  - What the container can check. The unauthenticated `GET /api` the start-up probe already makes lists each enabled realm with its `name` and `realmType` (`gw:src/main/java/com/lucidworks/cloud/gateway/security/api/ApiController.java:216-229`). The probe logs every enabled realm of type `trusted-http` by name, at warning level, with the sentence that its identity and groups header names must be in `BANANA_STRIP_HEADERS`. Under `BANANA_PREFLIGHT=strict` this is fatal unless the operator has acknowledged it by naming each such realm in `BANANA_ACK_TRUSTED_REALMS` (comma-separated realm names). The container cannot see the realm's header names, only that the realm exists, so the acknowledgement is a statement by the operator that the names are in the strip list, not a check of it. The acknowledgement setting is new, optional and affects only the probe's decision.
  - Detection is a start-up snapshot. The gateway registers and removes realms at run time (`gw:src/main/java/com/lucidworks/cloud/gateway/security/realm/CompositeAuthenticationManager.java:181-218`), and the start-up probe sees only the realms enabled at that moment. A Trusted-HTTP realm that an administrator enables, or whose header names they change, after the container started is not seen: there is no warning until the next start. Under `BANANA_PREFLIGHT=strict` that next start, on every replica, is refused until the new realm is named in `BANANA_ACK_TRUSTED_REALMS`, so a replica restarted for an unrelated reason can fail to come back. That is visible and loses nothing, but it is an availability effect operators should expect. `/healthz/upstream` (D11) repeats the realm check each time it runs, so a monitor that polls it sees a later realm within the cache interval; it is off by default, so by default the snapshot is the only check. Operators restart the container after any realm change.
  - What the acknowledgement does not cover. It is by realm name. A later change to the header names of a realm that is already acknowledged goes undetected, because the container never sees those names. A realm whose name contains a comma cannot be acknowledged, since the setting is comma-separated and the gateway puts no pattern on realm names (`gw:src/main/java/com/lucidworks/cloud/gateway/security/api/model/Realm.java:47-49`); under strict preflight such a realm blocks start with no way to acknowledge it, and the operator renames the realm or does not use strict.
  - A Fusion that has such a realm and an operator who does not read the log is the case the check cannot cover in the default (non-strict) mode: the container starts and the log carries the warning.
- Client `Authorization`, `x-api-key` and `Cookie` headers are forwarded as sent. They belong to the user, who could send them to Fusion directly; the container neither adds nor removes credentials.
- Fusion's audit log then records the container's address (or whatever an ingress in front of the gateway adds), and no client address, for all Banana traffic (`gw:src/main/java/com/lucidworks/cloud/gateway/config/AuditListenerConfiguration.java:241-246`). The container's access log (D11) is the place to correlate; see the residuals.

**D5. Cookies and TLS.**
- Browsers must reach the container over HTTPS. The container itself listens on plain HTTP on an unprivileged port and assumes TLS is terminated in front of it (ingress, load balancer, or a TLS-terminating proxy). It does not manage certificates.
- The proxy-to-Fusion hop is HTTPS and verified: `FUSION_TLS_VERIFY=on` is the default, with an optional CA file. (nginx does not verify upstream certificates unless told to.) Turning it off logs a warning at every start.
- An `http://` `FUSION_URL` is refused at start unless the development switch `BANANA_INSECURE_COOKIES=on` is set. The container sets `X-Forwarded-Proto` from the scheme of `FUSION_URL` (D4), and the gateway marks the session cookie `Secure` only when the request scheme or that header is https (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:98-100`), so an http Fusion URL would silently give the browser a session cookie without `Secure`. With the development switch on, the container already drops `Secure` and warns at every start, and the warning names the http upstream as well.
- Fusion sets the `id` cookie `Secure` because the proxied request is https (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:98-100`). The cookie has no `Domain`, so it binds to the container's host with no rewriting. By default the container passes it through untouched; the only exception is the development switch below, which removes the `Secure` attribute and nothing else. Passing it through is correct here and only here: the cookie belongs to the person who logged in.
- Plain HTTP exists only for local development: `BANANA_INSECURE_COOKIES=on` drops the `Secure` flag and logs a warning. Without it, a plain-HTTP deployment logs in successfully, the browser discards the cookie, and the app loops between login and itself.
- The container strips the upstream `Strict-Transport-Security` header (it would pin the container's host and subdomains to Fusion's policy) and sends its own only when `BANANA_HSTS=on`.
- Upstream names are re-resolved at run time through the system resolver, so a Fusion behind a load balancer whose address changes keeps working.

**D6. Login redirect and session lookup (small code changes, defaults reproduce 1.6.30).**
- A new optional setting (proposed name `FUSION_LOGIN_URL`) replaces the hard-coded `../login` in the 401 handler (`src/app/app.js:97-110`). Default `../login`. The root page's rendered configuration sets `/auth/login`, where Fusion itself sends unauthenticated users (`gw:src/main/java/com/lucidworks/cloud/gateway/config/SecurityConfig.java:147`). The way the `return` value is built (path, then hash, then the encoded query) is not changed in this work.
- Whether the `/auth/` login app, given `return=/` plus a hash, sends the browser back to the container is unverified (the app is not in the pinned sources). The pinned admin-UI login form does honour `return` (`fw:app/components/login/login-form/login-form.js:87-90`), so the documented fallback is `FUSION_LOGIN_URL=/admin/login`, a form that is open without a session (`gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewaySecurityConfig.java:61-95`) and needs only the routes in D2. It is the first item in the verification plan.
- A new optional setting (proposed name `FUSION_SESSION_API`) replaces the session URL built from the page's origin (`src/app/services/lucidworksSrv.js:14-15`). Default `/api/session`, a root-relative path that resolves to exactly the same URL in every browser for any page path. The container leaves it at the default.
- Both settings must be added to the defaults list or they are dropped (`src/app/components/settings.js:43-45`).
- The container refuses to start when `FUSION_LOGIN_URL` is a path under `/admin/` while `FUSION_PROXY_ADMIN_UI=off`, as it does for the mount with the admin route off (D1): the login page would be a 404 and every expired session would loop to it. The fallback login URL `/admin/login` therefore needs the admin route on.

**D7. Runtime configuration from environment variables.**
- At start the entrypoint renders two files from environment variables into a writable, container-local directory used for nothing else: one for `/config.js`, one for `/admin/banana/config.js` (D1). The web server serves each from an exact-match location (D2). The directory is not under the static root, so it is never served by the generic file handler, and the image's own `dist/config.js` is shadowed by the exact-match location and never served. The image never contains an environment-specific `config.js`, and the read-only image layers are never modified.
- Only keys that `settings.js` lists as defaults can be set (`src/app/components/settings.js:12-45`). The entrypoint rejects an unknown key rather than letting it vanish.
- Rendering is typed, not stringly. `USE_FUSION`, `USE_ADMIN_LUKE` and `USE_ADMIN_CORES` accept only `true` or `false` and are written as JSON booleans (the string `"false"` would be truthy in the app, `src/app/components/settings.js:16-24`). `panel_names` accepts a comma-separated list or a JSON array, each item restricted to letters, digits, `_` and `-`, and is written as a JSON array. Every other value is a string written as a JSON string literal with `<`, `>`, `&` and the line-separator characters escaped, so no value can end the script. Path values must begin with `/` and contain only URL path characters. A bad value stops the container with a clear message rather than writing a file that breaks the page.
- The preset (`BANANA_PRESET`) selects the key set. The Fusion preset uses the values 1.6.30 ships (`rel:src/config.js:36-80`); base's `/api/apollo/` defaults are not used, since 5.9.16 does not route them. The Solr preset (ADR 0006, ADR 0007) is outside this ADR, because the proxied routes and the trust model differ.
- No credential, API key or password is ever written to `config.js`; the container has none. The file is served to every visitor, including unauthenticated ones.

**D8. Caching.**
`index.html`, `config.js`, `app/components/require.config.js` and `app/dashboards/` are sent with `Cache-Control: no-cache` and a validator, so a changed `config.js` (same build revision, new content) or a new build is picked up on the next load. The other static files also use `no-cache` with validators; revalidation is cheap and avoids a stale module set after an upgrade. `config.js?r=<revision>` is matched by path, ignoring the query string.

**D9. Baseline security headers.**
Sent on every response the container itself generates (static files, errors, `/healthz`, the 421 page), with `always` so error pages carry them. Responses proxied from `/api`, `/api/`, `/auth/` and `/admin/` keep Fusion's headers (the login page and admin UI have needs this ADR has not measured), except for the HSTS handling in D5.

| Header | Value | Why |
|---|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval' https://api.github.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://*.tile.osm.org http://*.tile.osm.org; font-src 'self' data:; connect-src 'self' https://api.github.com; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'` | Allows what today's code needs and nothing else we know of. `unsafe-inline` for the inline bootstrap and handler, `unsafe-eval` for AngularJS and the template engine, api.github.com for gist save and load, the tile host for bettermap. The code requests tiles over plain `http://` (`src/app/panels/bettermap/module.js:270`), so both schemes are listed: on an https page a browser either upgrades or blocks that image as mixed content, and the policy must not be the reason it fails. Which of the two a current browser does for this host is unverified until a live run with the bettermap panel. Everything else, including the stored `solr.server`, can only reach the container's own origin. |
| `X-Frame-Options` | `SAMEORIGIN` | Same value Fusion uses; covers browsers that ignore `frame-ancestors`. |
| `X-Content-Type-Options` | `nosniff` | Matches Fusion. |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Fusion uses `no-referrer`. Map tile servers commonly expect an origin referrer (unverified), and Banana URLs carry state only in the hash, which browsers never send. |

> Update: the image's `script-src` no longer carries `'unsafe-inline'` or `'unsafe-eval'`; see [ADR 29](0029-content-security-policy-without-unsafe-eval.md). The rows of the table other than that policy are unchanged.

What this policy does and does not do, plainly. It stops framing from other origins, plugins, `<base>` and form hijacking, and it stops script and XHR from sending data to hosts other than the container and api.github.com. It does not stop a stored `{{...}}` from running, because `unsafe-eval` and `unsafe-inline` stay until the code stops needing them. Operators may append sources through documented variables, and `BANANA_CSP_MODE=report-only` exists to diagnose a violation before widening. The set is tightened only when the planned removal of inline script and `Function` use lands, and then by amending this ADR.

**D10. Identity: per-user login.**
Each person logs in on Fusion's own login page. The cookie is theirs; the container injects nothing. Everything Fusion enforces for that user (roles, blob permission, collection access) applies. The container has no Fusion credential setting at all, so no start-up checks on one are needed.

Residuals of per-user mode are recorded, not removed.
- **Same-site GET reach.** A request the browser makes with the `SameSite=Lax` cookie attached can reach a GET handler with that user's rights: a top-level cross-site navigation, and also a subresource request from a page on the same site (a sibling sub-domain embedding an image or script that points at the container), which is same-site and carries the cookie even without an `Origin`. It reaches GET handlers only and runs with the user's own rights. Fusion itself and 1.6.30 have the same exposure, since gateway CSRF protection is off (`gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewaySecurityConfig.java:201`). Under `/api/` the container closes it for browsers that send `Sec-Fetch-Site` (D3). It stays open for browsers that do not send the header, for requests that send `none` (a typed or bookmarked address, or a link opened from a desktop mail or chat application), and for the routes outside `/api/` (`/auth/`, `/admin/`, the static files), where Fusion serves no state-changing GET that Banana knows of (unverified for the admin UI).
- **Audience.** What a user can do through the container they can do against Fusion directly, only if the container's audience may already reach Fusion. That is the declared precondition under D2; the container narrows nothing for people who could reach Fusion, and widens the audience for people who could not.

**D11. Upstream failures, timeouts and visibility.**
- The proxy's read timeout is 60 s, above the gateway's 15 s limit on query routes, so the gateway's own answer is what the browser gets. What that answer looks like at the limit is unverified.
- Request bodies up to 10 MB are accepted (a saved dashboard was about 13 KB).
- Because the app swallows non-401 errors (`src/app/app.js:88-119`), the browser cannot report misconfiguration, so the container does. At start it validates its environment and makes one unauthenticated probe of `GET /api` on the Fusion URL (`gw:src/main/java/com/lucidworks/cloud/gateway/security/GatewaySecurityConfig.java:163`), logging the reported Fusion version, or a clear reason (DNS, TLS verification, not a Fusion). It also reads the enabled realms from the same response and logs each Trusted-HTTP realm by name (D4). This is a snapshot taken at start (D4). The probe warns and does not block start, so a restart during a Fusion outage still brings Banana up. `BANANA_PREFLIGHT=strict` makes it fatal, and an unacknowledged Trusted-HTTP realm is fatal under it too.
- `/healthz` reports the container only. `/healthz/upstream` runs the probe on demand, including the realm check, and reports each enabled Trusted-HTTP realm in its answer and its log without acting on it; it is for humans and monitors, not for the orchestrator's restart decision. It is off by default (`BANANA_HEALTH_UPSTREAM=on` enables it), it answers from a result cached for 10 s so a flood of requests makes at most one upstream call per interval, and it must not be exposed on the public ingress: a peer-address check would be meaningless behind a front end, so keeping it internal is the operator's job and is documented.
- Access logs go to standard output and record method, path without the query string, status and timing. They never record cookies, `Authorization`, API keys or the query string (the `apiKey` parameter can carry a key).

**D12. Container properties.**
Runs as a non-root user, listens on an unprivileged port, needs no writable path except a small tmpfs for the rendered configuration, stores nothing, and has no volume. No secret is baked into the image, and none is ever given to it, apart from the test-only digest key described under "Live-test instance digest" below, which is unset in every shipped configuration. Two containers behind one Fusion share nothing but Fusion.

**D13. The hosting layer adds nothing to saved dashboards.**
Dashboards written through a container have the same fields and relative `solr.server` as those written inside Fusion. A dashboard saved standalone opens inside Fusion 1.6.30 and the reverse.

## Not provided by this image

The container image implements per-user login only. Two other identity models are possible for an operator who builds them, and the owner's scope allows the first only "as a documented risky option": a **shared credential** (the proxy adds one Fusion API key or one HTTP Basic login to every request) and a **Trusted-HTTP front end** (an authenticating proxy sets an identity header and a Fusion Trusted-HTTP realm maps it to a user). Neither is built, tested or supported here. The project owner confirmed on 2026-11-06 that both are documented only and "not provided by this image", and that the image ships per-user Fusion login alone. This section is that documentation: it records what an operator would be taking on, so that the choice is made with the facts.

**A front end that injects credentials or identity headers in front of this image IS building one of those modes.** Nothing in the image has to change for that to happen: a front end that adds an `Authorization` Basic header, an API key or an identity header to requests it passes to the container creates the mode in the surrounding configuration. The image then forwards what it receives, because client credentials are forwarded as sent (D4), and passes the upstream `Set-Cookie` through (D5), so the shared account's session cookie reaches every visitor. The deletion of identity headers in D4 does not help here either: the front end's own injected header is what the container receives, and a header in the strip list is removed before Fusion sees it. The precautions below must be applied at that front end, and the walk-through rows marked "operator-built, not provided" (S7, S8, S23) describe what happens when they are not. The image has no setting that turns either mode on.

### Threat analysis

**The shared account's session cookie reaches every visitor (HTTP Basic).** With Basic injected, the gateway authenticates the request, creates or reuses a JWT for the shared account (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTConverterWebFilter.java:138-149`) and, because the proxy removed any inbound cookie, adds `Set-Cookie: id=<JWT>` to the response (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:41-68`). A proxy that passes upstream cookies on gives each visitor a copy of the shared account's session, which works directly against Fusion with no gate and no path restriction. Any restriction in the proxy is then moot for anyone who opens their browser's developer tools. API-key identities are exempt from the cookie (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:41-45`), so the leak is specific to Basic, but an API key carries no username, so saved dashboards would carry no author.

**The mode-switch hazard.** Cookies are host-only on the public host name. If an operator who ran a Basic-injecting deployment on a name later points the same name at this image (per-user mode), every browser that visited still holds `id` for the shared account. This image forwards the cookie, so those visitors are the shared account, including the admin UI where it is proxied, until the JWT expires, and they never see a login. This image cannot tell such a cookie from a legitimate one. The remedy is on the operator's side: use a new host name, or end the shared account's sessions in Fusion, before switching. Nothing in this image clears a cookie it did not set.

**A stale session cookie beats the trusted header (Trusted-HTTP front end).** The gateway tries the `id` cookie before the Trusted-HTTP header, and the first credential found is the one used (`gw:src/main/java/com/lucidworks/cloud/gateway/security/AuthenticationTokenConverter.java:72-79`, `gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/AuthenticationFilter.java:52-54`). The gateway also sets the cookie for the trusted identity on its first response (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:41-68`). When user A signs out of the single-sign-on front end and user B signs in on the same browser, the front end sends B's header, the browser still sends A's cookie, and B acts as A until that JWT expires. A front end that builds this must drop the upstream `Set-Cookie`, send `_cookie=false` on the upstream query, and delete the client's `Cookie` header.

**Trusted-HTTP trust is broader than an address check.** A request is trusted when the peer address matches or when any value of any configured trusted-proxy header matches (`gw:src/main/java/com/lucidworks/cloud/gateway/security/realm/trustedhttp/CompiledTrustedRealm.java:57-61`), and the token needs only the identity header (`gw:src/main/java/com/lucidworks/cloud/gateway/security/realm/trustedhttp/CompiledTrustedRealm.java:67-75`). The peer Fusion sees is the container, shared by everyone who can reach it, so an operator's own container must itself delete the identity and groups headers from everyone but the front end, delete the forwarded-address headers rather than rewrite them, and be unreachable except through the front end. This image does the deletion (D4) and relies on the realm's identity and groups header names being in its strip list, which is why that is a declared precondition and why the start-up probe names any enabled Trusted-HTTP realm.

**`/api/solr/` writes and cross-site GETs carrying cached Basic credentials.** A shared-credential proxy that allows `/api/solr/` passes every handler under it. Banana uses only read handlers (`select`, and the schema GETs), but the route also reaches the update handler (delete-by-query) and the Solr admin handlers; whether 5.9.16 forwards them is unverified. Browsers re-send cached HTTP Basic credentials with cross-site subresource requests, so with a Basic gate in front of the proxy an `<img>` or script on any web page visited by someone who passed the gate can make GET requests through the proxy with the injected credential. A proxy that did this also sees `Sec-Fetch-Site: cross-site` on those requests and must refuse them for every method, and refuse `same-site` as well.

**Blob scope and stored script.** The permission that covers dashboard saves is a glob on `/blobs/**` and cannot be narrowed to `resourceType=banana` (`gw:src/main/resources/init_roles.json:240-249`), so one identity that can save a dashboard can overwrite or delete every blob it can name, whatever its type. A stored `{{...}}` (see the residuals) runs with the viewer's identity; with one shared identity that is the shared account's powers for every viewer.

### Least-privilege role recipe (candidate, unverified)

**Update, 2026-11-06.** The recipe below was run on a live Fusion 5.9.16 system, as a non-admin user holding only this role, through the container. Querying, listing, loading and saving worked with the original six permissions. The stream, graph and document viewer panels needed three more `GET` permissions on the direct `/solr/` route: `/solr/*/stream`, `/solr/*/graph` and `/solr/*/schema/uniquekey`. The recipe applies to an operator who builds a shared identity, which this image does not provide; with per-user login each user's own Fusion roles apply. The text below is left as it was decided.

- GET `/collections` and GET `/collections/*/schema/*` (list, static and dynamic fields).
- POST `/query-pipelines/*/collections/*/select` and GET `/query-pipelines/*/collections/*/schema/uniquekey`.
- Only if dashboards name `/api/solr/`: POST `/solr/*/select`. Not `/solr/**`.
- GET, PUT and DELETE `/blobs/**`.
Do not use the shipped developer or admin roles. The recipe has not been run against a live system, and the narrowed globs (a single-segment `*` and the exact `/collections` form) are unverified; widen them to the shipped `/collections/**`, `/query-pipelines/**` form only after a failing check shows a needed path. **`/blobs/**` cannot be narrowed to `resourceType=banana`**: the same role can still read, overwrite and delete any blob by id, and a PUT to an existing id replaces it with no history (Live). Operators keep Banana users apart from users who manage other blobs.

### Precautions for an operator who builds either

These apply at whatever component injects the credential or identity: the front end in front of this image, or a proxy the operator writes.

1. Drop every upstream `Set-Cookie` header from responses (the cookie in the first threat above is how a shared identity leaks).
2. Add `_cookie=false` to every upstream query string, overwriting any client value, as defence in depth (`gw:src/main/java/com/lucidworks/cloud/gateway/security/filter/JWTCookieFilter.java:41-45`).
3. Strip client credentials before injecting your own: `Authorization`, `x-api-key`, the `apiKey` query parameter, `Cookie`, and the identity and groups headers. Pin the login `realmName` too, because the converter takes it from the client's query (`gw:src/main/java/com/lucidworks/cloud/gateway/security/AuthenticationTokenConverter.java:48-52`).
4. Refuse cross-site requests for every method, using `Sec-Fetch-Site` (`cross-site` and `same-site`) and the `Origin` check in D3. Delete `X-Forwarded-For`, `X-Real-IP` and `Forwarded` from client requests instead of rewriting them (see D4).
5. Allow only the paths and methods Banana uses (matching on the normalized path, D2), and do not proxy `/auth/` or `/admin/`, or the login and logout verbs on `/api/session`.
6. Put real authentication in front: a gate that authenticates people, not a network position.
7. Switch modes only on a new host name (see the mode-switch hazard).

### Why the image does not ship them

Each of them makes the container the thing that holds or asserts a Fusion identity, and then every error in the container is a privilege problem in Fusion. The three problems above are not hypothetical: the shared Basic mode leaks the account's session by default, the Trusted-HTTP mode lets a stale cookie outrank the header, and a shared proxy that opens `/api/solr/` opens writes the app never uses. Guarding each needs its own start-up checks, allowlists, header handling and live tests against a Fusion that needs a realm or a role created for the purpose, which the available test system does not allow. The per-user mode needs none of that, serves every purpose Banana has, and keeps Fusion as the only place identities and permissions are decided.

## Consequences

**Better.** There is one supported way to run Banana outside Fusion, and it works with Fusion 5.9.16 without any change to Fusion. People log in with their own Fusion accounts. The container holds no Fusion credential, so there is no shared identity to leak or to protect. It has a defined set of security headers and a defined, small attack surface. The hazards of shared and trusted-header identities are written down for anyone who builds them. Operators get log lines for the failures the app hides.

**Costs and behaviour changes.**
- Two small settings are added to the app (login URL, session path). Their defaults reproduce 1.6.30, so a build served inside Fusion does not change.
- The proxy's Host and Origin checks are new behaviour that blocks a foreign page or an unexpected host name from using the container. Legitimate same-origin use on the public name is unaffected. The public origin is mandatory.
- A Banana user who needs a Fusion SSO login, or an operator who wants a shared or header-based identity, is not served by the image.
- The CSP keeps `unsafe-eval` and `unsafe-inline`, so it reduces framing and egress risk but does not stop stored script. (Superseded: the image's policy now drops both keywords, [ADR 0029](0029-content-security-policy-without-unsafe-eval.md). It stops inline script and `javascript:` links; it still does not stop an AngularJS expression written into a page, see [ADR 0032](0032-angularjs-1-0-8-stays.md).)
- Operators must terminate TLS in front of the container, set the public origin, preserve `Host` at any front end, deploy only where the container's audience may already reach Fusion's API, and put the identity and groups header names of every enabled Fusion Trusted-HTTP realm into `BANANA_STRIP_HEADERS`.
- `/api/` requests that a browser marks `cross-site` or `same-site` are refused with 403, which is stricter than 1.6.30 for a link followed from another site.
- The first start has no migration: nothing is stored and nothing is written to Fusion.
- An `http://` `FUSION_URL` stops the start unless the development switch is on, and a Trusted-HTTP realm enabled after start is seen only at the next start (D4, D5).

**Constraints on later work.**
- Live-test instance digest. The guarded live-test client (ADR 0008, "A guarded client is the only way live tests write or delete dashboards") confirms which Fusion instance a container talks to with a keyed digest header, and may start the hosting image for that purpose. The image must therefore emit one response header (indicative name `X-Banana-Upstream-Digest`) carrying the HMAC-SHA-256, under a key taken from a per-run environment variable (indicative name `BANANA_LIVE_DIGEST_KEY`), of its upstream Fusion origin, and nothing else, ONLY when that variable is set. The variable is unset by default in every image and in the compose example, so a shipped image sends no header derived from its upstream and no default changes. The key is never logged, written to a file, rendered into `config.js` or echoed in the access log, and the header is the one response header outside the baseline set in D9. An image that did not implement this could not be used by the live browser leg, which then refuses to run rather than skipping the check.

**Release-note text (proposed).** "Banana can now be run outside Fusion as a container that serves the app and proxies the Fusion API on the same origin. Users log in with their own Fusion accounts. The container holds no Fusion credential. Inside Fusion nothing changes."

**Companion decisions.** ADR 0004 records why the inside-Fusion layout is verified only by imitation, and depends on this decision's mount; it is accepted together with this one. ADR 0005 records that hosting Banana on a different origin from Fusion is not supported.

## Verification plan

Unit and component tests, runnable without Fusion, using a stub upstream that records what it receives:
- Host and Origin handling (D3): public, alias, listed-redirect and unknown `Host`; absent, own, allowed, foreign and `null` origins; the stub sees the rewritten `Origin` and `Host` only on allowed requests; 403 or 421 before the upstream for the rest; redirects built from the configured origin only; `/healthz` exempt.
- Forwarding headers (D4): a client-supplied `X-Forwarded-For`, `X-Real-IP` and `Forwarded` never reach the stub and the container writes none of its own; the built-in strip list never reaches the stub; `BANANA_STRIP_HEADERS` adds to the built-in list, and an empty value leaves the built-in list in force; an invalid name stops the start; `X-Forwarded-Proto` comes from the scheme of the Fusion URL; an `http://` Fusion URL stops the start unless `BANANA_INSECURE_COOKIES=on`, and with it on the start-up log names the http upstream.
- `Sec-Fetch-Site` (D3): `cross-site` and `same-site` on `/api/` get 403 for GET, HEAD, POST, PUT and DELETE and never reach the stub; `same-origin`, `none` and an absent header pass.
- `Sec-Fetch-Site` outside `/api/` (D3), two separate tests. GET and HEAD pass: GET and HEAD with `cross-site`, `same-site`, `same-origin`, `none` and no header on `/`, `/auth/`, `/admin/`, `/config.js` and exact `/api` are never refused by the rule. Cross-site writes are refused: POST, PUT and DELETE with `Sec-Fetch-Site: cross-site` on `/auth/` and `/admin/` get 403 and never reach the stub, while the same methods with `same-site`, `same-origin`, `none` and no header are not refused by the rule.
- Host and Origin normalization (D3): an explicit default port equals none, case differences are ignored, a non-default port is significant; a write to a listed redirect host gets 421; `/healthz/upstream` is subject to the `Host` check; a rewritten `Host` gets 421; exact `/admin/banana` answers 308 with `Location: /admin/banana/` (a relative reference with no scheme or host, also when the request came in on an allowed second name) with the mount on and 404 with it off. A `Host` header without a port is compared against the default port of the scheme of the origin it is compared with; a redirect-host entry without a port does not match the same name on another port; a front end that sends a listed redirect host as `Host` gets 308 on GET (the documented loop), not forwarding.
- Route table and matching (D2): exact `/api` passes GET and HEAD and refuses POST; `/api/` passes all methods; `/api/blobs?resourceType=banana` and `/api/collections` (no trailing slash) reach the stub; encoded, dot-segment and doubled-slash forms of `/admin/banana/`, `/config.js` and `/healthz` never reach the stub; raw backslash and control characters give 400; the original request URI reaches the stub unchanged.
- Config rendering (D7): escaping of hostile values, typed booleans (`false` is a boolean, not a string) and arrays, rejection of unknown keys and bad paths, both rendered files, no secret in either, exact-match serving of `/config.js` over a `dist/config.js` that is also present.
- Mount (D1): `/admin/banana/config.js` leaves the login URL at `../login`; start refuses the mount with the admin route off.
- Cache headers (D8) and baseline headers (D9) on every static response and error page; upstream HSTS stripped.
- Login-URL and session-path settings (D6): default reproduces the 1.6.30 redirect string and URL; a custom value is used.
- Start-up probe (D11): messages for DNS failure, TLS failure, non-Fusion response, and success; strict mode refuses to start. Against a stub whose `GET /api` lists a `trusted-http` realm: the realm is logged by name, strict mode refuses to start, and naming the realm in `BANANA_ACK_TRUSTED_REALMS` lets it start. A login URL under `/admin/` with the admin route off refuses to start. `/healthz/upstream` repeats the realm check on each uncached run. A realm name containing a comma cannot be acknowledged and so blocks a strict start. `/healthz/upstream` is off by default and cached when on.
- Logs contain no cookie, `Authorization`, key or query string.
- The container runs as non-root, has no writable path beyond the configuration tmpfs, and its image history and files contain no secret.

Acceptance runs that need the real Fusion 5.9.16 (the stub cannot prove gateway behaviour):
1. Proxied login through `/auth/login` with a return path that points at the container, including a hash, and the same through `/admin/login`. This decides which login URL the root page uses and whether the admin route can default to off. **Unverified today.**
