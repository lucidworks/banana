# 0012. The live smoke test: one fixture dashboard, direct Solr route for stream panels

Date: 2026-11-06
Status: Accepted

## Context

Banana's unit tests cannot show that a build renders its panels against a real search backend, that the login through the same-origin proxy works, or that Banana's own save, load and delete screens work on Fusion. The guarded live-test client (see the decision on the guarded client) exists so that a test can do those things on a shared Fusion without being able to damage it. This record covers the smoke test built on it: what it opens, how it decides that a panel rendered, and three choices that a later maintainer would otherwise have to rediscover.

Facts the choices rest on, all observed on Fusion 5.9.16 with the test collection of 240 generated documents:

- The default query pipeline route, `/api/query-pipelines/_system/collections/<collection>/`, answers `select` with 200 but answers `stream` and `graph` with 500: the pipeline allows no custom request handlers. The panels that build stream expressions (time series, significant terms, graph) therefore stay empty on that route. Each of the three shows an error banner that starts "This panel requires direct Solr access." and ends with the status, "(The request failed (HTTP status 500))", and the graph panel draws nothing. Each panel sends at least one request on first load (a run on 2026-11-07 saw three failed requests, one per panel; a panel that refreshes after the time picker sets its filter sends more), and the browser logs one failed resource load for each.
- The direct route, `/api/solr/<collection>/`, answers `select`, `stream` and `graph` with 200 for a user with enough rights.
- A dashboard's server comes from the dashboard itself (`solr.server`), so one saved dashboard uses one route for all its panels.
- The panels of a dashboard start querying before the time-picker panel has set its filter. A dashboard with an empty filter list makes the histogram panel fail with a `TypeError` on first load; the bundled dashboards avoid it by shipping the time filter in the saved filter list.
- The login application loads its components lazily. A fill or click that happens before they are ready is lost without an error.
- The Bettermap panel requests tiles from public tile servers. The test browser's rule set aborts every request to another origin, and the browser then logs a console error for each. (Correction, 2026-11-07: this record first said that the map panel did too; the map panel draws vector data from files that ship with Banana and requests no tiles.)

## Options considered

1. **Use the default pipeline route for the fixture and list the three stream panels as exceptions.** Rejected: three of the configured panel types would never be exercised against data, and the code that builds their expressions (the part most likely to break in a bundler change) would go untested.
2. **Fixture on the direct route only, no record of the pipeline route.** Rejected: the pipeline route is what a default install uses, and Fusion's refusal is the reason the fixture avoids it. A change in Fusion's behaviour should be noticed.
3. **Fixture on the direct route, plus one small test that saves a variant on the pipeline route and asserts the documented failure.** Chosen.
4. **Fail on any console error.** Rejected: the aborted tile requests are caused by the test's own rule set, not by Banana.
5. **Take the login helper as it was and retry the whole test when login hangs.** Rejected: the failure is a lost click inside the helper, about every other run, and a retry of the test costs a new dashboard save each time.

## Decision

- `test/live/banana-it-dashboard.json` is a dashboard on the `banana-it-logs` collection with one panel of each of the types in `panel_names`, each configured with fields of the generated documents. It uses the direct route `/api/solr/`, an absolute time range that covers the data, a time filter in the saved filter list, an empty extra-parameters field, no index interval, and no table option that sends a GET `select`, all of which the guarded client's rules need (see its record). A unit test checks that the fixture covers exactly the configured panel types.
- `test/live/smoke.spec.js` logs in through the proxied login, saves a copy of the fixture through the guarded client, opens it, and requires every panel to pass its rule (`test/live/panels.js`: one rule per panel type) and no error banner. The rules of the data panels look for something only the data produces: the map needs at least 8 regions with a fill other than the neutral one (the generated documents carry 8 country codes), the time series needs a number of 100 or more on its value axis (a zero-filled series ends near 1), the graph needs at least one node in the graph the panel was given, the ticker needs a number before its percent sign (the panel prints `?%` when it has nothing to compare), and the others look for facet counts, table rows, chart canvases with the 240 hits, and similar. The five control panels (column, time picker, query, filtering and text) show no data; their rules check only that they are on the page with their expected content. It then saves the open dashboard under a new title through Banana's Save screen, confirms it with an independent GET, reopens it, deletes it through the Load screen, confirms the 404, and checks that the fixture copy is still there before removing it through the client.
- Console errors fail the test, except a failed resource load whose URL is on another origin (the aborted tile requests). The pipeline-route test additionally allows the failed-request console errors for `stream` and `graph` (status 500), and nothing else: the graph panel no longer throws when its request fails.
- A fourth test saves a variant with only the control and stream rows on the pipeline route, and requires 500 answers for `stream` and `graph`, three failed-request banners, and three panels with no data (no time series values, at most a header row of significant terms, no graph nodes). If Fusion starts allowing those handlers, this test fails and the fixture can move to the default route.
- The login helper of the client module changes in two ways, and neither touches a rule of the guard. First, it waits for the page to go quiet and, if no login request is seen within 8 seconds, sets the fields and clicks again, up to four times, only if no login request was sent; it still sends the same single login request, and a click is repeated only when no login request was seen within an 8 second window (a login that Fusion answers slowly is waited for, up to 60 seconds, not sent again): a request that was sent is never sent again, however late or with whatever status it is answered. Without this, about half of the runs lost the click on the lazily loaded login page and hung. Second, it sets the user name and password inside the page and empties the password field as soon as the request is answered, instead of using `locator.fill`. `fill` writes the value it was given into Playwright's call log ("fill(...)"), and the call log is part of every error message that the runner prints and stores.
- Error artefacts are disabled for live runs. Playwright can write a page snapshot (`error-context.md`) when a test fails, and a trace, a screenshot or a video; on a failed login any of them can hold what was typed into the login page. The live configuration sets trace, screenshot and video to `off`, sets `PLAYWRIGHT_NO_COPY_PROMPT` (the runner skips the failure snapshot when it is set; the configuration sets it when it loads and the launcher sets it for the runner), and writes the runner's output to a fresh temporary directory outside the repository that the launcher removes after the run. A unit test fails if the configuration enables any of these or puts the output inside the repository, and a browser test fails a login against a local stand-in with a recognisable password and counts the files of the output directory and of the work tree that contain it (none).
- The Protractor tests and configuration no longer exist (the unit-test harness decision removed them); this test is the end-to-end check that replaces them.

## Consequences

- The smoke test needs a Fusion with the generated test collection and credentials in the environment. It is not part of CI. Each run saves up to three dashboards named with the run's identity and removes each of them.
- A panel whose rule is too loose could pass while rendering little; the rules check for content that only the data can produce, but a rule must be updated together with the fixture when a panel's configuration changes. Unit tests check that every rule rejects a panel that rendered but holds nothing, and that the map, time series, graph and ticker rules reject their no-data forms.
- The smoke test does not log the browser out between tests: in one run a browser login made right after a browser logout was answered with 401 on every call, so the browser logout is left to the guarded client's own spec.
- A dashboard that Banana saved with the time picker in absolute mode stores the range as dates but not as the range objects the ticker panel reads, so the ticker throws a `RangeError` when such a dashboard is reopened; the last release has the same code. The test that reopens the copy saved through the Save screen names that one error as known and fails on any other. Later change (see 0030): the time filter now reads its date objects from the stored range, so the ticker no longer throws; the live test no longer tolerates the error (changed without a live run).
- A failed run leaves no snapshot, trace, screenshot or video to delete; the runner's output directory is temporary.
- The graph panel used to throw when a graph request failed (its failure handler asked the panel to render, and the render read the graph before it was ever set). It now clears the graph and draws nothing, so the pipeline-route test allows no script error; a `TypeError` there is a failure.
- Opening a dashboard while the default dashboard is still loading races inside Banana: the route change replaces the current dashboard with an empty object, and the default dashboard's collection-list request then writes `core_list` into it, which throws "Cannot set properties of undefined (setting 'core_list')". A user can hit it by switching dashboards quickly. The last release has the same code. The smoke test does not tolerate the error: it waits for the default dashboard to finish loading before it opens the dashboard under test. The race itself was left unfixed in this record. Later change (see 0030): a collection list that arrives after the dashboard that asked for it has been replaced is now ignored, so the error no longer occurs; the smoke test keeps waiting for the default dashboard anyway.
